# ADR-016: AuditLog Ownership — `backend-auth` Authoritative Writer, `backend-compliance` Read-Only Consumer

- **Status:** Accepted — ratified by the commissioning human decision recorded in this record (2026-07-14).
- **Date:** 2026-07-14
- **Scope:** State ownership / module boundary — the shared-write `state-audit-log` domain (`AuditLog` model, `backend/prisma/schema.prisma:507-533`) written today via `BaseService.logAudit` from at least eight modules (`backend/src/modules/{attendance,quality,crm,users,auth,work-requests}/service.ts`, confirmed by grep, plus others sharing the same base-service helper), and the proposed `SPEC-COMPLIANCE-001` (target `docs/03-modules/compliance/MODULE_SPEC.md`, currently `.gitkeep` only). Also settles Compliance's positive capability scope: governance, verification, reporting, policy evaluation, evidence generation, and regulatory workflows.
- **Supersedes:** none (additive; resolves the open human-authority item `SYNC-005`/`SIR-GLOB-006` specifically as it bears on `state-audit-log`, and closes the Compliance-specific escalation `SYNC-035`/`SIR-COMPLIANCE-001`/`OD-COMPLIANCE-001` that was blocked on it). `SYNC-005`/`SIR-GLOB-006`'s other half — `state-user`'s dual-writer ambiguity between `backend-auth` and `backend-users` — is **not** addressed by this record and remains OPEN.
- **Change class:** Material architecture/ownership decision requiring a Decision Record per Constitution §6/§7, mirroring the precedent of `ADR-011`–`ADR-015`. This record settles the boundary only; authoring `docs/03-modules/compliance/MODULE_SPEC.md` (`SPEC-COMPLIANCE-001`) is a further, separate Documentation Workflow action this ADR unblocks but does not itself perform.

## Problem

A Boundary Collision Gate (G1.5) run for a proposed `SPEC-COMPLIANCE-001`, 2026-07-14 (`SYNC-035`), returned **FAIL** before authoring began: the strongest direct code evidence for Compliance's real-world scope — the `// COMPLIANCE MODULE //` comment directly above the `AuditLog` model definition (`backend/prisma/schema.prisma:507-509`) and CRR §30's "every important action is logged... immutable" requirement — pointed at a state domain, `state-audit-log`, that was already a recorded shared-write collision with `authoritative_writer: UNKNOWN` (`.claude/knowledge/STATE_OWNERSHIP_INDEX.yaml:27`; `SYNC-005`; `SIR-GLOB-006`, OPEN — BLOCKED since 2026-07-04). Authoring a Compliance specification that claimed any relationship to `AuditLog` — as sole writer, as read-only governor, or by silent omission — risked resolving or pre-empting that pending decision rather than disclosing it, which is outside Lead Architect authority. The gate stopped rather than pass silently, exactly as `SYNC-023`/`SYNC-027`/`SYNC-031` did for the structurally identical Contracts/Chatbot/Payslips collisions before their respective ADRs.

Unlike those three precedents — where a second module's *specification* was the competing claimant — the disputed party here was the pre-existing `state-audit-log` shared-write ambiguity itself: eight-plus modules write `AuditLog` rows today via the shared `BaseService.logAudit` helper, with no single module named as authoritative writer anywhere in the knowledge layer.

## Decision

1. **`backend-auth` is the authoritative writer of `state-audit-log` (`AuditLog`).** This resolves `SYNC-005`/`SIR-GLOB-006`'s `state-audit-log` half. Rationale: `AuditLog.actor`/`actor_role` are keyed to `User` (auth's own state domain), `backend-auth` already owns the platform's other security/audit-adjacent state (`Session`, `PasswordResetToken`), and consolidating the shared `BaseService.logAudit` write path under the module that already owns the identity/security context each entry references is the narrowest change consistent with today's code shape — every existing call site continues to write through the same shared helper; no module's calling code changes as a result of this record alone (see Compatibility).
2. **`backend-compliance` is a read-only consumer of `AuditLog`.** It owns no `AuditLog` state, lifecycle, or write API. Any Compliance capability that surfaces audit-log content (governance reporting, regulatory evidence, verification) reads it through an interface `backend-auth` exposes (a future `IF-AUTH-*`/`IF-AUDIT-*` contract — not yet named, tracked as an open decision, see below), never by direct table access and never by writing to `AuditLog` itself.
3. **Compliance's positive capability scope is settled as: compliance governance, verification, reporting, policy evaluation, evidence generation, and regulatory workflows.** These are orchestration/reporting capabilities that consume state owned by other modules (AuditLog from `backend-auth`; Retention's deletion-audit surface per `docs/03-modules/retention/MODULE_SPEC.md` Out of Scope; Consent per `ADR-015`'s "Compliance consumes Consent for governance/audit only"; Documents per `docs/03-modules/documents/MODULE_SPEC.md` `OD-DOC-012`) — Compliance owns no upstream state of its own beyond whatever governance-artifact/report state it may define within its own specification (e.g., a compliance-report or evidence-package entity, if one is confirmed by CRR/PDD during authoring).
4. **Compliance does not own `AuditLog` state, lifecycle, or write APIs**, now or in any future revision without a superseding Decision Record.
5. The other 7+ modules that currently call `BaseService.logAudit` directly (`attendance`, `quality`, `crm`, `users`, `auth`, `work-requests`, and others sharing the helper) are unaffected by this record: they continue writing `AuditLog` rows through the existing shared helper. This ADR designates `backend-auth` as the domain's *accountable* owner for governance/architecture purposes (the module whose future evolution of the `AuditLog` schema, retention tagging, and any read-API surface is authoritative) — it does not, by itself, require refactoring every existing call site into a new service boundary. That refactor, if pursued, is a separate, future implementation decision out of this record's scope.

## Alternatives Considered

- **Assign `backend-compliance` as authoritative writer of `AuditLog`.** Rejected by the commissioning human decision: Compliance has no code today (`.gitkeep` only), while `AuditLog` is live, already-written, security-critical state; routing every existing writer's audit calls through a not-yet-built module would be a much larger, riskier change than consolidating ownership under the already-adjacent `backend-auth`, and would conflate "governs/reports on" with "is the system of record for."
- **Leave `state-audit-log` at `authoritative_writer: UNKNOWN` and let Compliance proceed with a narrower scope (governance/verification/reporting/policy-evaluation/evidence-generation/regulatory-workflows only, explicitly deferring `AuditLog`).** Considered and rejected as the sole disposition at the prior G1.5 stop (`SYNC-035`/`DECISION_INDEX.md`'s Compliance section) as "not the objective actually requested" — the target spec's clearest evidence centers on `AuditLog`, and shipping a spec that silently avoids the repository's plainest evidence for the module's purpose would risk a second, narrower ownership claim needing correction later, the same anti-pattern `SYNC-023` avoided for Contracts. This ADR instead resolves the underlying ambiguity so Compliance's real scope, including its consumption of `AuditLog`, can be documented accurately.
- **Assign no single writer and instead formally bless `BaseService.logAudit`'s current shared-write pattern as permanently ownerless (a platform utility, not a module-owned domain).** Rejected: Constitution §7 requires every state domain to resolve to a single accountable owner for architecture-review purposes; "shared utility, no owner" is the status quo this ADR is meant to close, not a target state.

## Compatibility

Strictly additive to the knowledge/governance layer. No code changes are required by this record alone: every module's existing `BaseService.logAudit` call site is unchanged. `.claude/knowledge/STATE_OWNERSHIP_INDEX.yaml`'s `state-audit-log` row is updated (`authoritative_writer: UNKNOWN` → `backend-auth`) as a synchronization action performed under this ADR's authority, not part of the ADR text itself. `docs/03-modules/compliance/MODULE_SPEC.md` may now be authored against this settled boundary as a separate Documentation Workflow action. `state-user`'s dual-writer ambiguity (the other half of `SYNC-005`/`SIR-GLOB-006`) is untouched.

## Reversibility

Reversing this decision would require a new ADR that supersedes it, plus a corrective edit to `SPEC-COMPLIANCE-001` (once authored) and to `SPEC-AUTH-001` if either had come to assume this boundary in a way the reversal would falsify. No data is uniquely stored by this record; `AuditLog` rows already written are unaffected either way.

## Consequences

- **Positive:** `SYNC-005`/`SIR-GLOB-006` is resolved for its `state-audit-log` half (the `state-user` half remains open, tracked separately). `SPEC-COMPLIANCE-001` may now be authored against a settled, non-competing boundary — Compliance's clearest owned-state candidate is redirected from "own AuditLog" to "consume AuditLog read-only via backend-auth's interface," consistent with how Compliance already consumes Consent (`ADR-015`) and Retention's deletion-audit surface. Future preflight and boundary-collision passes reach this conclusion immediately from the governance layer instead of rediscovering the ambiguity.
- **Negative / cost:** `backend-auth`'s specification (`SPEC-AUTH-001`, `docs/03-modules/auth/MODULE_SPEC.md`) does not yet document owning `AuditLog`; a future correction pass to that document is required to disclose this ADR's assignment (tracked as a new open item for that module, not performed by this record). No `IF-AUTH-*`/`IF-AUDIT-*` read-interface contract is named yet for Compliance's consumption — this is an explicit open decision `SPEC-COMPLIANCE-001`'s authoring must disclose, not silently assume a shape for.

## Human Decision Required

None outstanding for the ownership question itself — this record *is* that decision. The following remain open, unaffected by this ADR: owner *assignment* for `backend-auth`/`backend-compliance` (named accountable person/team, blocked on `SYNC-001`/`SIR-GLOB-001`); `state-user`'s dual-writer ambiguity (`SYNC-005`/`SIR-GLOB-006`, `state-user` half only); the concrete shape/name of the `AuditLog` read-interface Compliance will consume (an open decision for `SPEC-COMPLIANCE-001`'s own authoring); whether `SPEC-AUTH-001` requires a corrective revision disclosing its now-explicit `AuditLog` ownership (a future Documentation Workflow action against that module, not this record).
