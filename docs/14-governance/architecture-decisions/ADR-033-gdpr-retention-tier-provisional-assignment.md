# ADR-033: GDPR Retention-Tier Assignment — Provisional Mapping Now, Tax-Advisor Sign-Off Tracked Separately (Non-Blocking)

- **Status:** Accepted — ratified by the commissioning human on 2026-07-28, resolving `GD-09` (GDPR retention-tier assignment & Retention module). Authored by the Lead Architect from `docs/implementation/GOVERNANCE_DECISIONS_REQUIRED.md`'s GD-09 entry and the commissioning human's explicit approval of Option (c).
- **Date:** 2026-07-28
- **Scope:** Platform-wide GDPR retention-tier mapping for every record type CRR §25 did not already assign to one of its three tiers. Resolves: `SPEC-NOTIF-001` `OQ-NOTIF-02`, `SPEC-AUTH-001` `OQ-AUTH-11`, `SPEC-HR-001` `OD-HR-11`, `SPEC-DOCUMENTS-001` `OD-DOC-001`, `SPEC-CHATBOT-001` `OD-CHAT-019`, `SPEC-CONSENT-001` `OD-CONSENT-003`, `docs/03-modules/onboarding/MODULE_SPEC.md` `OPQ-1` (partial — see Decision point 4), and the retention module's own `SIR-RETENTION-006` aggregation row. Does **not** resolve `OD-RETENTION-01`/`SIR-RETENTION-002` (the tax-advisor sign-off itself, which is tracked as a separate, non-blocking follow-up per Decision point 3) nor `OD-RETENTION-05`/`10`/`11`/`14`/`15` (RBAC, cross-module authorization, sweep query design, owner assignment, and fan-out workload — none of which are tier-mapping questions).
- **Supersedes:** none (additive). Extends CRR §25's three-tier framework (already fixed: Tier 1 = 6mo shift-coordinates, Tier 2 = 5yr general personal/profile, Tier 3 = 6yr payroll/tax-adjacent) to record types CRR §25 left unassigned.
- **Change class:** Platform/compliance architecture decision per Constitution §6/§7, mirroring the `ADR-032` (GD-12) precedent of separating a within-repository-control decision from an external dependency rather than letting the external dependency block everything.

## Problem

CRR §25 defines three GDPR retention tiers with concrete windows, but most record types across the platform have never been mapped to one of them: `Notification` (`OQ-NOTIF-02`), `User`/`Session`/`AuditLog` (`OQ-AUTH-11`), HR contract documents (`OD-HR-11`), uploaded/work-permit documents (`OD-DOC-001`), chatbot conversation-adjacent records (`OD-CHAT-019`), consent records (`OD-CONSENT-003`), and Onboarding's Personalfragebogen data (`OPQ-1`, already tier-assigned in prose but carrying an explicit tax-advisor sign-off gate). Separately, CRR §25 itself carries an `[ACTION]`: a client tax-advisor sign-off is required before the mapping is legally final, and that sign-off has an external, uncontrollable lead time.

As originally framed (`GOVERNANCE_DECISIONS_REQUIRED.md`'s GD-09 "Recommended: (a), after tax-advisor sign-off"), the mapping decision and the external sign-off event are conflated into a single blocking gate — meaning seven-plus module specs' retention-tier rows, and the entire `backend-retention` module build, stay open indefinitely for a reason (external timeline) that has nothing to do with whether the repository's own architecture is ready.

## Decision

1. **Every previously-unassigned record type is now assigned to one of CRR §25's three existing tiers, as a provisional, disclosed-as-provisional mapping:**
   - `Notification` (`OQ-NOTIF-02`) → **Tier 2 (5-year general)**. Operational/personal in character, no payroll/tax adjacency, no shift-coordinate adjacency; the notification content will generally reference general personal data (assignment/task context), not payroll figures.
   - `User`, `Session`, `AuditLog` (`OQ-AUTH-11`) → **Tier 2 (5-year general)** for `User` and `Session`. `AuditLog` is **explicitly excluded from all three tiers and retained indefinitely** — it is the platform's own accountability record (CRR §30's "every important action is logged" mandate), and deleting audit history on the same clock as the data it describes would defeat its purpose; this mirrors `OD-RETENTION-08`'s own framing in `SPEC-RETENTION-001` for Retention's own audit trail.
   - HR contract document/PDF/scan (`OD-HR-11`) → **Tier 3 (6-year payroll/tax-adjacent)**. A signed employment contract is itself a payroll/tax-relevant record under German retention law (the same statutory basis, §257 HGB/§147 AO, already cited for Onboarding's IBAN/Tax-ID fields), not merely "general personal data" — treating it as Tier 2 would risk under-retaining a document the tax authority may expect for the full 6-year window.
   - Uploaded/work-permit documents (`OD-DOC-001`) → **split by document class**: work-permit/legal-employment-authorization documents → **Tier 3** (same statutory-adjacency reasoning as the HR contract above); general uploaded documents (anything not employment-authorization-adjacent) → **Tier 2**. `backend-documents` must record a per-document tier field at upload time, not a single module-wide default.
   - Chatbot conversation-adjacent records — metadata and spend counters (`OD-CHAT-019`) → **Tier 2**. Transcripts, contingent on `OD-CHAT-008`'s still-open transcript-persistence question, inherit whichever tier applies to the personal data they contain once that question is resolved; this ADR does not itself decide whether transcripts are persisted at all.
   - Consent records (`OD-CONSENT-003`) → **Tier 2**. Consent-acceptance metadata is general personal/profile data; no payroll or coordinate adjacency applies.
   - Onboarding's Personalfragebogen data (`OPQ-1`) → **no change** — Onboarding's own spec already states the correct split (general fields Tier 2, IBAN/Tax-ID Tier 3); this ADR ratifies that existing split as no-longer-provisional-pending-a-separate-decision, but the tax-advisor sign-off `OPQ-1` itself names remains open per Decision point 3 below, identically to `OD-RETENTION-01`.

2. **This mapping is explicitly provisional, not a legal certification.** Every module spec amended by this decision must state the assigned tier is provisional pending tax-advisor sign-off (`OD-RETENTION-01`), not asserted as final. Engineering (schema fields, sweep-job configuration, `backend-retention`'s own build) may proceed against this mapping now.

3. **Tax-advisor sign-off (`OD-RETENTION-01`/`SIR-RETENTION-002`) is tracked as a separate, non-blocking follow-up — it blocks *legal certification* of the mapping, not this decision, not `backend-retention`'s build, and not any dependent module's own G2 freeze.** If the tax advisor later requires a different mapping for any record type than what this ADR assigns, the fix is a bounded, mechanical migration (update the affected rows' `retention_tier` value and re-run the sweep's next cycle against the new window) — not a redesign of the sweep engine, which is tier-agnostic by construction (`SPEC-RETENTION-001`'s own category-driven design).

4. **No change to CRR §25's own three tier definitions or windows.** This decision only extends the mapping to previously-unassigned record types; it does not revisit the 6-month/5-year/6-year windows themselves, which remain the client's own confirmed requirement.

## Rationale

- **Separates a within-repository decision from an external dependency**, mirroring `ADR-032`'s (GD-12) same move: the architecture question (which tier does this data belong to) is answerable today from the data's own character and existing statutory citations already in CRR/PDD/module specs; the legal-certification question (does the tax advisor agree) has its own timeline and does not need to gate engineering progress.
- **Compliance exposure is reduced, not increased, by deciding now.** Leaving seven-plus record types with no retention policy at all (the status quo) is a worse compliance posture than operating under a disclosed-provisional mapping with a defined re-mapping path if corrected later.
- **The mechanical cost of being wrong is bounded.** `backend-retention`'s sweep design (per `SPEC-RETENTION-001`) is already category-driven (a registered category maps to a tier, the sweep executes per-category) — changing which tier a category maps to is a configuration/data change, not a rearchitecture.
- **Consistent treatment of `AuditLog`:** excluding it from all three tiers (rather than defaulting it to Tier 2) is required by CRR §30's own indefinite-retention framing for the platform's accountability record, and mirrors `OD-RETENTION-08`'s identical reasoning already recorded for Retention's own audit trail — this ADR makes that reasoning explicit for `backend-auth`'s `AuditLog` too, closing a gap the original `OQ-AUTH-11` row did not resolve on its own.

## Consequences

- Every affected spec's tier-assignment row is updated from "Open — required disposition before G8 Release Readiness" (or equivalent) to "Resolved (provisional), `ADR-033`" — disclosing the assigned tier and the still-open tax-advisor sign-off, per module, at that module's next amendment pass (tracked below, applied as part of this same Governance Resolution decision).
- `backend-retention`'s own `SIR-RETENTION-006` aggregation row (which only records that `SPEC-RETENTION-001` inherits, and does not itself resolve, the per-module tier questions) is updated to reflect that its aggregated items are now individually resolved (provisionally) at the source-module level; `SIR-RETENTION-006` itself is not deleted (append-only convention) but is annotated as no longer blocking on that basis.
- `OD-RETENTION-01`/`SIR-RETENTION-002` (tax-advisor sign-off) remains OPEN, explicitly reclassified from "blocks the mapping decision" to "blocks legal certification of an already-decided provisional mapping, non-blocking for engineering" — tracked to closure exactly as before, just no longer gating anything else.
- Knowledge-layer updates required (tracked as an exit condition of this ADR's ratification): none of `.claude/knowledge/*.yaml` currently encode retention-tier assignments per record type (confirmed absent — these are documentation-layer facts living in each module's own spec), so no `DEPENDENCY_GRAPH.yaml`/`STATE_OWNERSHIP_INDEX.yaml` edit is required by this decision; `docs/implementation/GOVERNANCE_DECISIONS_REQUIRED.md`'s GD-09 row should be marked Decided with a pointer here; `docs/05-execution/EXECUTION_DASHBOARD.md` should reflect GD-09 as decided (mapping) with the tax-advisor sign-off called out as the sole remaining, non-blocking item.

## Compatibility

No runtime behavior changes as a result of this record alone — no code exists yet for `backend-retention`, and no other module's persisted schema changes as a direct effect of this ADR (per-record `retention_tier` fields are this decision's *output* for each module's own future implementation work, not a migration this record performs). No rollback concern.

## Scope note

This settles retention-tier *mapping* only (`GD-09`'s mapping half). It does not resolve `backend-retention`'s own remaining open decisions (`OD-RETENTION-05` Admin RBAC scope, `OD-RETENTION-10` cross-module delete authorization, `OD-RETENTION-11` sweep query design, `OD-RETENTION-14` owner assignment, `OD-RETENTION-15` fan-out workload) — each remains OPEN under its own row, tracked in `docs/implementation/GOVERNANCE_REGISTER.md`, and handled on its own track per the Governance Resolution workflow. It also does not resolve `OD-CHAT-008` (whether chatbot transcripts are persisted at all) — chatbot transcripts' own tier is contingent on that separate, still-open decision.
