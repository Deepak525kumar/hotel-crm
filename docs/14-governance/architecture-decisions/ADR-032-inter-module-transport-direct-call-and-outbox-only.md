# ADR-032: Inter-Module Transport — Direct Service Calls (Synchronous) + the Existing Outbox (Asynchronous/Durable) Are the Sole Platform Standard; No Generic Event Bus

- **Status:** Accepted — ratified by the commissioning human on 2026-07-28, resolving `GD-12` (Platform event-bus / inter-module transport). Authored by the Lead Architect from `docs/implementation/GOVERNANCE_DECISIONS_REQUIRED.md`'s GD-12 entry and the commissioning human's explicit approval + clarification.
- **Date:** 2026-07-28
- **Scope:** Platform-wide inter-module transport convention. Resolves every module spec's "candidate-level only" event/interface framing where the blocking cause is GD-12: `SPEC-HR-001` `OD-HR-04`, `SPEC-EMP-001` `OD-EMP-09`, `SPEC-CALENDAR-001` `OD-CAL-06`/`OD-CAL-08`, `SPEC-CONSENT-001` `OD-CONSENT-005`, `SPEC-CRM-001` `OD-CRM-12`, `SPEC-DOCUMENTS-001` `OD-DOC-009`, `SPEC-CHATBOT-001` `OD-CHAT-023`.
- **Supersedes:** none (additive/ratifying). Formalizes the pattern already in use by `backend-notifications` (`ADR-029`, GD-01) and `backend-calendar` (direct `AssignmentService` call, `calendar/service.ts:9-14`), rather than introducing a new mechanism.
- **Change class:** Platform architecture decision per Constitution §6/§7, mirroring the `ADR-021`/`ADR-029` precedent. This record settles the transport convention only; it does not itself freeze any REVIEW spec or author new code beyond the relabeling described in Consequences.

## Problem

Seven module specifications (HR, Employee-Management, Calendar, Consent, CRM, Documents, Chatbot) each independently describe a required cross-module effect — e.g., Calendar's sick/vacation mark must cancel the worker's same-day assignment and notify their manager — using a placeholder `EVT-*`/`IF-*` ID and explicitly label the transport "candidate-level only," because no platform convention exists to answer: *is a cross-module effect a same-process function call, or a durable published event a consumer subscribes to independently?* Absent an answer, each spec author invents a bespoke shape or leaves it "TBD," and — as `backend-calendar`'s own code comment already discloses (`calendar/service.ts:9-14`) — the actual shipped code already resolved this pragmatically (a direct call to `AssignmentService`) without a ratifying decision to point to.

Separately, `backend-notifications` (`ADR-029`, GD-01, Accepted and built) already implements a durable, asynchronous, at-least-once delivery mechanism — a transactional `OutboxEvent` table drained by a dedicated Platform Worker process — for every notification a producer module enqueues. This is a working, production-adjacent reference implementation for the "durable/async" half of the open question; the "synchronous, must-happen-atomically-with-its-trigger" half (e.g., calendar's auto-cancel) has no equivalent formal ratification, only the informal precedent already in code.

## Decision

1. **Direct, in-process service-to-service calls are the platform standard for synchronous cross-module operations** — an operation whose effect must complete (or fail) atomically with, or immediately after, its trigger, within the same request/transaction boundary. Example: Calendar's same-day auto-cancel calling `AssignmentService.update()` directly (already shipped, `calendar/service.ts:87-106`). No new abstraction, wrapper, or dispatcher is introduced for this case — a producer imports and calls the consumer's service class directly, exactly as calendar already does.

2. **The existing Outbox (`OutboxEvent` model + Platform Worker, `ADR-029`) is the sole approved mechanism for asynchronous, durable work** — anything that must survive a crash, may be retried, does not need to complete before the producer's own request returns, or fans out to a delivery channel outside the request/response cycle (push, email, SMS, webhook). A producer enqueues an `OutboxEvent` inside its own write transaction; the Worker drains it independently. This is already how every notification producer (work-requests, work-applications, attendance, quality, calendar) operates today.

3. **No generic event bus, message broker, or pub/sub dispatcher exists in this architecture, and none is introduced by this decision.** There is no third transport option. Every cross-module effect this platform needs falls into (1) or (2); a module spec that cannot express its need in one of those two categories has not yet correctly scoped the effect, not discovered a gap in this decision.

4. **If a future architectural need genuinely requires pub/sub, fan-out-to-unknown-consumers, or distributed messaging beyond what a direct call or the Outbox can express, that need requires its own new ADR — it is explicitly out of scope for this decision and must not be retrofitted onto either mechanism above.** This decision is not a placeholder for a future bus; it is the platform's answer for as long as it remains modular-monolith-shaped, and any expansion is a fresh architectural choice, not an extension.

## Rationale

- **Ratifies working code, invents nothing:** both mechanisms already exist and run (Outbox: `ADR-029`, merged Epic 7; direct call: `calendar/service.ts`'s shipped auto-cancel). This decision closes the "candidate-level only" gap seven specs share without requiring a migration of any kind.
- **No infrastructure the CRR/PDD never asked for:** a real message bus (Redis Streams, SQS, a generic pub/sub layer) would be a large infrastructure commitment with new failure modes (broker availability, ordering, replay) that no confirmed requirement calls for, consistent with Constitution §6 (do not invent unconfirmed architecture).
- **A firm two-option boundary, not a third abstraction:** a lightweight "in-process domain event" wrapper (dispatch-by-name to registered handlers, still same-process/same-transaction) was considered and rejected as an unnecessary third category — it would cost real implementation effort across 6+ producers/consumers for organizational clarity only, with no new capability over a direct call. Where a spec's own event ID (e.g., `EVT-CAL-SickVacationMarked`) survives this decision, it is retained as a **documentation label** for "the moment the direct call or Outbox enqueue happens," not as evidence of a dispatcher that doesn't exist.

## Consequences

- Every affected spec's `[OPEN]`/"candidate-level" `EVT-*`/`IF-*` transport row is reclassified, per spec, as either "direct in-process service call" or "Outbox-backed asynchronous delivery," using the criterion in Decision points 1–2 (does the effect need to be atomic with its trigger, or can it be eventually-delivered). This is documentation relabeling per the affected spec's own next amendment pass, not new code — each spec's existing acceptance criteria for the underlying business behavior are unchanged.
- `SPEC-CALENDAR-001` `OD-CAL-06` (manager-notification transport) and `OD-CAL-08` (formal event schema) are resolved: the notification is Outbox-backed (already true in shipped code, `calendar/service.ts:113-142` calling `notificationService.enqueue()`); the auto-cancel is a direct call (already true, `calendar/service.ts:87-106`). No code changes; the spec's own "implementation-time default, not a full resolution" framing is superseded — this is now the ratified resolution.
- `SPEC-EMP-001` `OD-EMP-09`, `SPEC-HR-001` `OD-HR-04`, `SPEC-CONSENT-001` `OD-CONSENT-005`, `SPEC-CRM-001` `OD-CRM-12`, `SPEC-DOCUMENTS-001` `OD-DOC-009`, `SPEC-CHATBOT-001` `OD-CHAT-023` are resolved at the **transport-convention** level only — each spec's own event/interface rows must still be individually classified into (1) or (2) at that spec's next revision; this ADR does not itself rewrite every `EVT-*`/`IF-*` row (that is a per-spec documentation-workflow action, tracked below), but it removes the platform-level blocker that made every one of those rows "candidate-level only."
- Knowledge-layer updates required (tracked as an exit condition of this ADR's ratification, not performed by this record alone): `.claude/knowledge/DEPENDENCY_GRAPH.yaml` should record every direct-call producer→consumer edge explicitly (calendar→assignments already implicit in code, not yet in the graph) and every Outbox-backed edge should cite `ADR-029` + this record; `docs/implementation/GOVERNANCE_DECISIONS_REQUIRED.md`'s GD-12 row should be marked Decided with a pointer here; `docs/05-execution/EXECUTION_DASHBOARD.md` should drop GD-12 from its open-decisions framing.

## Compatibility

No runtime behavior changes as a result of this record alone — both mechanisms it ratifies are already live in shipped code (`ADR-029`'s Outbox; calendar's direct call). No migration, no rollback concern. This record assigns platform-wide accountability for a convention that already exists in practice; it relocates no code and mandates no rewrite.

## Scope note

This settles the inter-module transport convention only (`GD-12`). It does not resolve any individual module's remaining non-transport open decisions (e.g., `SPEC-CALENDAR-001`'s `OD-CAL-04` timezone anchor, `OD-CAL-07` RM edit scope, `OD-CAL-10` operations-stub disposition, `OD-CAL-11` auto-cancel/broadcast ripple; `SPEC-HR-001`'s `OD-HR-01a` module-boundary dispute; or any other module's own product/architecture open items) — each remains OPEN under its own row, tracked in `docs/implementation/GOVERNANCE_REGISTER.md`, and handled on its own track per the Governance Resolution workflow.
