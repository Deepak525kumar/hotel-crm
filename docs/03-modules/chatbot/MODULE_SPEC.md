## Purpose and Scope

**Outcome:** Establish Chatbot as the single, implementation-independent capability owning all AI-execution behavior in the platform — conversation lifecycle, LLM provider integration (Claude API, model selection), prompt construction, conversation orchestration, context assembly, tool execution, conversation memory/session state, token/cost management, guardrails, and AI audit — per `ADR-013`'s settled ownership boundary, so that Onboarding (document-collection conversation, CRR §8) and, forward-looking, Compliance (GDPR subject-rights requests, CRR §8 line 110, §26 line 343) can each trigger and consume a chatbot conversation through `IF-CHATBOT-*` interfaces instead of independently implementing agent execution.

**In scope:**

- **Current:** Nothing is implemented. `backend/src/modules/chatbot/` holds only `.placeholder`; it is not imported or route-mounted (`backend/src/routes/v1/index.ts`, full file read); no Claude/Anthropic SDK dependency exists (`backend/package.json`, full dependency list read); no Prisma model exists for any conversation/session entity (`backend/prisma/schema.prisma`, grep-confirmed absent); `.claude/knowledge/MODULE_REGISTRY.yaml:202-212`, `.claude/knowledge/DEPENDENCY_GRAPH.yaml:40-43`, and `.claude/knowledge/API_INDEX.yaml:32-34` all independently record `backend-chatbot` as a placeholder-unregistered/declared-but-unimplemented stub.
- **Target — conversation lifecycle & orchestration:** An AI agent (not a static wizard) using the Claude API guides document collection during onboarding: it asks the worker for all required documents and, if incomplete, asks again for the missing ones (CRR §8 lines 103-105,107).
- **Target — LLM provider / model selection:** Claude Haiku is the recommended, adopted model (cheapest confirmed option) (CRR §8 line 109; PDD §4.14 line 151, §7.1 line 266, §11 line 442). "Provider abstraction" in the sense of a provider-swappable layer is `ADR-013`'s boundary language, not a CRR/PDD requirement — CRR/PDD confirm only the one adopted provider/model pairing.
- **Target — context assembly:** Accepting the consumer-supplied context a conversation needs at start — for Onboarding, the worker's required-document/completeness state (`onboarding/MODULE_SPEC.md` §6.3 lines 149-150); Chatbot never initiates a conversation independent of a triggering consumer (`ADR-013` item 3).
- **Target — token/cost management:** A hard monthly token budget cap stored in config, a per-conversation token limit, a cached required-document list, and graceful fallback to a static checklist UI when limits are hit (CRR §8 line 109; PDD §4.14 line 151, §5.6 line 192 "Chatbot budget guard" job, §7.1 lines 267-268, §11 line 442). Chatbot owns the guardrail/decision to trigger fallback; the consumer only reacts to the signal (`ADR-013` item 3; `onboarding/MODULE_SPEC.md` §16.1).
- **Target — guardrails:** Transport (TLS in transit, not end-to-end encrypted) and input-validation/injection-defense guardrails for the conversation itself, including accepted-upload-type enforcement as a conversation-level guardrail (`onboarding/MODULE_SPEC.md:325`; PDD §5.2; `ADR-013`) — **scoped (v0.1.1, `FIND-ARCH-01`) to lightweight, conversational type/format hints only (e.g., confirming a stated file type/format with the worker), independent of whether Chatbot ever handles file bytes directly (`OD-CHAT-003`), and distinct from Documents' own byte-level storage-layer validation (`RULE-DOC-09`)** — see `OD-CHAT-007` for a disclosed tension between the two layers' accepted-type sets.
- **Target — AI audit:** Conversation-level logging (start/end, fallback triggers) for compliance and dispute resolution, consistent with the platform's general audit-log mandate (CRR §30) and `onboarding/MODULE_SPEC.md:360`'s reference to "Chatbot conversation started/ended (timestamp, [OPEN] conversation transcript retention)".
- **Target — secondary use (forward-looking, Compliance-owned workflow, Chatbot-executed):** The same agent is reused for GDPR subject-rights (data access/export) requests (CRR §8 line 110; CRR §26 line 343). `docs/03-modules/compliance/` holds only `.gitkeep` — no Compliance module specification exists yet to confirm this consumption contract from the other side; this is recorded here as a one-sided boundary assertion (mirrors `docs/03-modules/documents/MODULE_SPEC.md`'s `OD-DOC-012` treatment of its own Compliance-forward-looking edge).
- **Target — tool execution / conversation memory:** Named by `ADR-013` as owned responsibility classes; CRR/PDD confirm no concrete tool call and no explicit memory/persistence model — see `OD-CHAT-002`, `OD-CHAT-003`, `OD-CHAT-008`.

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6)

- **The onboarding business workflow itself** — onboarding state and its transitions, onboarding steps (Personalfragebogen, document-collection *orchestration decision-making*, contract-signing coordination, pool/claim, hire approval), onboarding-specific validation, onboarding completion signaling, and onboarding's own business rules are owned by Onboarding (`docs/03-modules/onboarding/MODULE_SPEC.md`). Onboarding triggers a Chatbot conversation and reacts to its outcome; it does not implement, configure, or operate the agent (`ADR-013` items 2-3).
- **Document storage** — document lifecycle, metadata, upload mechanism, storage abstraction (S3 EU), version history, categories, permissions, access, retrieval, and archival are owned by Documents (`backend-documents`, `SPEC-DOCUMENTS-001`). Documents' own specification independently frames Chatbot as "a distinct capability... Documents is the storage/retrieval target the chatbot's document-collection flow writes to and reads from, not the chatbot itself" (`documents/MODULE_SPEC.md:34`) — consistent with, not contradicting, this module's boundary. Whether Chatbot's own (unconfirmed) tool-execution surface ever calls Documents' upload interface directly, versus file upload being an entirely separate non-conversational UI action, is disclosed as open, not resolved, at `OD-CHAT-003`.
- **The GDPR subject-rights workflow and fulfilment ownership** — request intake, response assembly, and delivery to the data subject are conceptually owned by Compliance (CRR §8 line 110, §26 line 343); Chatbot only executes the conversation Compliance's workflow triggers (`ADR-013` item 3). No Compliance specification exists yet (`docs/03-modules/compliance/` holds only `.gitkeep`).
- **Employee/account lifecycle and activation** — whether an onboarding account activates is Onboarding/Employee-Management's decision, not this module's; Chatbot emits a completion/fallback signal only (`onboarding/MODULE_SPEC.md:150`; `ADR-013`).
- **Contract lifecycle** — owned by `backend-hr`/`SPEC-HR-001` per `ADR-012`; unrelated to this module.
- **Retention-sweep execution, consent governance, special-category field-governance policy** — conceptually Compliance's, unrelated to this module beyond disclosing which retention tier Chatbot's own records fall under, where determinable (`OD-CHAT-019`).

**Non-goals:** (confirmed out of the platform entirely, or explicitly excluded by CRR/PDD)

- Any marketplace-era concept — none existed in the marketplace-era data model and none is reintroduced here.
- Background checks, account lockout, login rate-limiting, CAPTCHA — explicitly excluded platform-wide (CRR §2 lines 32-35, §3 line 39); **not** to be conflated with the separate, unresolved question of a conversation-level cost/abuse-prevention control for this module's own token-metered endpoint (`OD-CHAT-010`).
- Payroll computation of any kind (CRR §23) — unrelated to this module.
- Qualified Electronic Signature (QES) / e-signature integration — unrelated to this module (CRR §9 lines 118-119).

## Ownership and Boundaries

**Module owner:** `unassigned` — reserved human authority (`SYNC-001`; `MODULE_REGISTRY.yaml:205`). No code exists for this capability today (see Evidence and Traceability).

**Owned state:**

- **Current:** None. No Prisma model exists (grep-confirmed against `backend/prisma/schema.prisma`); this capability holds zero business state today.
- **Target (proposed, unowned until a human/architecture decision assigns `backend-chatbot`'s state domain):** `ChatbotConversation` (proposed name — **not sourced from PDD §9.3, which is entirely silent on any Chatbot-owned entity**, a stricter gap than Documents' `WorkerDocument` naming, which PDD did name; see `OD-CHAT-001`). Proposed minimum fields: conversation id, worker id, purpose/consumer type (document-collection vs. subject-rights), status (in-progress / completed / fallback-triggered), model/provider used, token-spend counters, timestamps. Transcript-content persistence is separately open (`OD-CHAT-008`).

**Consumed state (owned elsewhere, referenced never redefined):**

- Worker identity — owned by the `User`/`HotelWorker` state domains (`DEPENDENCY_GRAPH.yaml:63,66`) — read-only, as the actor a conversation is bound to.
- Document-completeness/required-document context — supplied at conversation start by the triggering consumer (Onboarding today; sourced ultimately from Onboarding's `PersonalData`/nationality and Documents' completeness state, neither of which this module redefines) — read-only, per-conversation input only, not persisted as this module's own state beyond whatever the proposed `ChatbotConversation` record captures.
- Subject-rights request context (forward-looking) — owned conceptually by Compliance, not yet specified — read-only, per-conversation input only.

**Permitted writes (target only; none current):** `ChatbotConversation` rows (proposed) and their own audit-trail entries (via the shared `BaseService.logAudit` pattern every other module uses). This module would never write `WorkerDocument` (Documents), `Contract` (`backend-hr`), `User`/`HotelWorker`/employment-status, `PersonalData` (Onboarding), or retention-execution state.

**Boundary/non-responsibilities:**

- This module does **not** own the onboarding business workflow (Onboarding), document storage/lifecycle (Documents, `SPEC-DOCUMENTS-001`), contract lifecycle (`backend-hr`, `ADR-012`), employee/account activation (Onboarding/Employee Management), or the GDPR subject-rights workflow/fulfilment itself (Compliance, conceptual).
- **Ownership challenge (Boundary Loop) — for the state proposed above, owner/readers/writers/consumers are proven or escalated:**
  - `ChatbotConversation` (target, proposed) — Owner: **proposed** `backend-chatbot`, unratified. Writers (target): `backend-chatbot` only, once it exists. Readers (target, inbound consumer edges): Onboarding (start/status/outcome); forward-looking, Compliance (subject-rights, no spec exists). **Not proven** — no state-domain id exists yet in `DEPENDENCY_GRAPH.yaml` (`OD-CHAT-014`); a proposed ownership assertion pending human/architecture ratification, mirroring `documents/MODULE_SPEC.md`'s identical `OD-DOC-004` treatment.
  - **The G1.5 collision this module's authoring was originally blocked on** (`onboarding/MODULE_SPEC.md`'s pre-`ADR-013` first-person execution-ownership claim over Chatbot) is now resolved: `ADR-013` settles that `backend-chatbot` owns AI-execution and `backend-onboarding` owns the business workflow only, consuming Chatbot via `IF-CHATBOT-*`.   - **Documents' framing of Chatbot** ("a distinct capability... not the chatbot itself," `documents/MODULE_SPEC.md:34`) is independently consistent with this boundary — no collision.

## State and Lifecycle

**Current:** No state exists. No `ChatbotConversation`/any-name model, no lifecycle, no states, no transitions are implemented anywhere in the repository.

**Target lifecycle (reasoned from the confirmed capability boundary and CRR/PDD; states beyond entry/completion/fallback are not explicitly enumerated by either authority — labelled open, not assumed):**

- **Entry:** A conversation is created when a consumer (Onboarding today; Compliance, forward-looking) calls `IF-CHATBOT-StartConversation` **in-process**, from its own already-authenticated request handler (`OD-CHAT-004`'s two-part resolution, v0.1.2 — see Interfaces and Contracts), supplying worker id, purpose, and context (CRR §8 lines 103-110; `onboarding/MODULE_SPEC.md` §6.3).
- **Turns:** The worker and agent exchange messages; the agent tracks required-item completeness against the supplied context (or, for subject-rights, whatever Compliance's own request context specifies, forward-looking and unconfirmed).
- **Completion:** All required items in the supplied context are satisfied → outcome `completed`, signal emitted to the consumer.
- **Fallback:** Monthly or per-conversation token limit exceeded (confirmed), or Claude API unavailable for reasons other than budget (unconfirmed whether the identical path applies, `OD-CHAT-012`) → outcome `fallback-triggered`, signal emitted to the consumer; the static checklist UI is rendered and owned by the consumer, not this module.
- **No entity name is assigned by PDD §9.3** — this specification proposes `ChatbotConversation`, explicitly disclosed as its own proposal, not CRR/PDD-sourced (`OD-CHAT-001`), mirroring the provenance-disclosure pattern `documents/MODULE_SPEC.md` uses for its own task-scoped "canonical boundary" items (`FIND-CONS-DOC-007`).
- **Retention/persistence:** whether conversation transcripts are persisted beyond conversation completion, and whether engaging the chatbot requires explicit data-processing consent, is genuinely unresolved. This is the **same open question** already recorded as Onboarding's own `OPQ-3`, which itself states resolution ownership sits with this module ("This is a Chatbot-module (`backend-chatbot`) decision per `ADR-013`"); recorded here as `OD-CHAT-008`, cross-referencing Onboarding's `OPQ-3` rather than duplicating it as an independently-discovered gap.
- **Concurrency:** Unaddressed by CRR/PDD for this capability — labelled unknown (`OD-CHAT-016`), consistent with the identical gap already recorded for `backend-hr` (`OD-HR-08`) and Documents (`OD-DOC-011`).

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:** Not evaluable for current state (nothing is implemented). Target: a monthly-cap or per-conversation-limit breach triggers the confirmed graceful fallback (`RULE-CHAT-03`); whether a raw Claude API outage (distinct from budget exhaustion) triggers the identical path, and what retry/backoff policy applies, is unspecified by CRR/PDD (`OD-CHAT-012`, `OD-CHAT-015`).

**Trust boundaries/authorization:** Current: no route exists; nothing to evaluate. Target: every worker-facing conversation-turn/status call MUST bind to the authenticated actor's own identity — a conversation id or worker id MUST NOT be accepted as a bare, unverified client-supplied parameter (`RULE-CHAT-09`, `REQ-CHAT-013`). Broader document-level-style RBAC/permission granularity (who besides the owning worker — a manager, an auditor, or Compliance for a subject-rights request — may access a conversation or its outcome) is **not specified anywhere in CRR/PDD**, mirroring `documents/MODULE_SPEC.md`'s `OD-DOC-005`/`OD-DOC-007` treatment — elevated here to **blocks G2 Specification Freeze** (`OD-CHAT-005`), given this module handles sensitive personal data and, for its secondary use, GDPR-subject-rights-adjacent content. **Resolved, two-part, v0.1.2 correction of the v0.1.1 text (Architecture re-review `FIND-05`, High — the v0.1.1 blanket "direct access" claim conflated this module's genuinely worker-facing conversation turn with its module-to-module orchestration calls):** (1) the worker's client talks **directly** to Chatbot's own end-user-facing, `auth-middleware`-protected API surface for the live conversation turn (`IF-CHATBOT-ExchangeMessage`) and for its own status polling (`IF-CHATBOT-GetConversationOutcome` mode a) — citing the same platform-wide precedent that every other registered module consumes `auth-middleware` directly for its own routes (`DEPENDENCY_GRAPH.yaml:381-399`) and that no service-to-service/internal-API-key/mTLS authentication mechanism exists anywhere in this codebase (`backend/src/middleware/`, `backend/src/lib/` — confirmed absent); (2) Onboarding's/Compliance's own module-to-module orchestration calls (`IF-CHATBOT-StartConversation`; `IF-CHATBOT-GetConversationOutcome` mode b) are **in-process service calls** trusted within the same process boundary — no new authentication infrastructure is invented or required because no HTTP/network hop occurs for these calls, mirroring the `notification-service` in-process singleton-call pattern already used platform-wide (`.claude/knowledge/DEPENDENCY_GRAPH.yaml:82-89,334-344,431`). Both parts are disclosed, cited resolutions, not silent assumptions, and remain subject to human/architecture ratification at G2 like every other author-proposed reading in this document; `RULE-CHAT-09`'s self-scoping invariant continues to govern only the two genuinely worker-facing call paths in part (1), unaffected by part (2)'s in-process reclassification.

**Data classification/retention:** Conversation content is personal data at minimum (identity information, document references, worker-supplied text) and, for the subject-rights secondary use, may carry the full content of a GDPR export request. TLS-in-transit applies; not end-to-end encrypted (`RULE-CHAT-07`, restating — not newly deriving — the same in-transit expectation `onboarding/MODULE_SPEC.md:325` states for its own transmission leg). Encryption-at-rest for any persisted conversation content is unaddressed and contingent on `OD-CHAT-008` resolving toward persistence (`OD-CHAT-018`, mirroring `documents/MODULE_SPEC.md` `OD-DOC-017`). Retention-tier assignment (which of CRR §25's three automatic-deletion tiers applies to conversation-adjacent records) is unresolved (`OD-CHAT-019`, mirroring `OD-DOC-001`/`OD-HR-11`). Whether worker conversation content could ever incidentally intersect CRR §27's special-category fields (Konfession, disability, health) is unconfirmed — no CRR/PDD statement addresses conversational content specifically, distinct from the document *types* Documents already tracks as open (`documents/MODULE_SPEC.md` `OD-DOC-002`).

**Performance budgets/workload:** No explicit SLO is defined in CRR/PDD for conversation-turn latency. Design intent: the confirmed token caps (monthly + per-conversation, `RULE-CHAT-03`) function as a cost-bound control, not a latency SLO. **Strengthened, v0.1.1 (`FIND-PERF-CHAT-003`):** unlike Documents' low-frequency, headcount-bounded workload shape, this module's workload is qualitatively different — **`PIVOT_DESIGN_DOCUMENT.md` §5.1 (line 155) names chatbot explicitly, alongside notifications, as an anticipated "high-load module"** whose clear internal module boundaries justify later extraction from the modular monolith ("...so that any high-load module (notifications, chatbot) can be extracted later if needed"), and every conversation turn is a synchronous, user-facing, blocking call to an external third-party LLM (Claude API) — not reused verbatim from Documents' generic bounded-workload deferral framing. Concrete latency/throughput budgets are still deferred to implementation and not asserted here (Constitution §6). `OD-CHAT-015` (no retry/backoff/timeout policy for Claude API unavailability) is cross-referenced here as a **latency/capacity/backpressure concern**, not solely a failure-mode concern: an un-timed-out synchronous call to an external provider directly threatens request-handler/connection-pool exhaustion under load. A new open decision, `OD-CHAT-022`, requires a concrete timeout/backpressure policy for the synchronous Claude API call before launch, distinct from (but related to) `OD-CHAT-015`'s retry/backoff question. Once a `ChatbotConversation` schema exists, queries should be indexed at schema-creation time per `OD-CHAT-020` (revised v0.1.1 to ground the indexing need in this module's own confirmed access pattern rather than asserting the worker-id+purpose/status shape outright), mirroring the platform-wide missing-compound-index finding already recorded for Documents (`OD-DOC-019`) and Quality (`FIND-PERF-003`).

**Observability/audit:** No audit behaviour is implemented (nothing exists). Target: conversation-level audit-log entries for start/completion/fallback (`RULE-CHAT-10`, `REQ-CHAT-014`), consistent with the platform's shared `AuditLog` pattern (`base-service.ts`) and CRR §30's general mandate. Full transcript-content logging/retention is a separate, still-open question (`OD-CHAT-008`).

**AI-specific guardrail note (new to this module's capability class):** Prompt-injection resistance — a risk class specific to LLM-backed agents, distinct from the generic "injection defense" `onboarding/MODULE_SPEC.md:325` attributes to this module's conversation guardrails — is not addressed by any CRR/PDD or cross-spec source. This is flagged as a new, non-fabricated concern, **elevated v0.1.1 to blocks G2 Specification Freeze given this is the single most central abuse vector for a module whose core purpose is executing an LLM agent on untrusted worker input, reused for the more sensitive GDPR subject-rights flow** (`OD-CHAT-006`, `FIND-SEC-004`) — a required interim mitigation posture (system-prompt/user-input separation, tool-call allowlisting contingent on `OD-CHAT-002`, treating model output as untrusted) is now stated there, not left silent, analogous to how `documents/MODULE_SPEC.md`/`hr/MODULE_SPEC.md` flag malware/content-scanning as a deferred-not-silent position (`OD-DOC-016`/`OD-HR-14`).

**Abuse-prevention note:** CRR §2 confirms **no login rate-limiting** platform-wide (CRR §2 line 34) — but this is distinct from the unresolved question of whether a conversation-level rate-limit/abuse-prevention control applies to this module's own cost-incurring endpoint(s) (each conversational turn spends real LLM tokens); the two must not be conflated. **Named abuse shape (v0.1.1, `FIND-SEC-005`):** a single authenticated worker (or a small number of colluding/compromised accounts) can issue many conversation-starts/turns in a short window, each individually under the per-conversation limit, collectively exhausting the *shared* monthly budget and forcing `JOB-CHATBOT-BudgetGuard`'s platform-wide fallback for all other workers — a shared-resource-exhaustion/financial-harm vector via a single actor, distinct from CRR §2's login-rate-limiting exclusion (`OD-CHAT-010`).
