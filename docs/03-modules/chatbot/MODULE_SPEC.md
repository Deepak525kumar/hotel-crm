## Purpose and Scope

**Outcome:** Establish Chatbot as the single, implementation-independent capability owning all AI-execution behavior in the platform — conversation lifecycle, LLM provider integration (Claude API, model selection), prompt construction, conversation orchestration, context assembly, tool execution, conversation memory/session state, token/cost management, guardrails, and AI audit — per `ADR-013`'s settled ownership boundary, so that Onboarding (document-collection conversation, CRR §8) and, forward-looking, Compliance (GDPR subject-rights requests, CRR §8 line 110, §26 line 343) can each trigger and consume a chatbot conversation through `IF-CHATBOT-*` interfaces instead of independently implementing agent execution.

**In scope:**

- **Current:** Nothing is implemented. `backend/src/modules/chatbot/` holds only `.placeholder`; it is not imported or route-mounted (`backend/src/routes/v1/index.ts`, full file read); no Claude/Anthropic SDK dependency exists (`backend/package.json`, full dependency list read); no Prisma model exists for any conversation/session entity (`backend/prisma/schema.prisma`, grep-confirmed absent); `.claude/knowledge/MODULE_REGISTRY.yaml:202-212`, `.claude/knowledge/DEPENDENCY_GRAPH.yaml:40-43`, and `.claude/knowledge/API_INDEX.yaml:32-34` all independently record `backend-chatbot` as a placeholder-unregistered/declared-but-unimplemented stub.
- **Target — conversation lifecycle & orchestration:** An AI agent (not a static wizard) using the Claude API guides document collection during onboarding: it asks the worker for all required documents and, if incomplete, asks again for the missing ones (CRR §8 lines 103-105,107).
- **Target — LLM provider / model selection:** Claude Haiku is the recommended, adopted model (cheapest confirmed option) (CRR §8 line 109; PDD §4.14 line 151, §7.1 line 266, §11 line 442). "Provider abstraction" in the sense of a provider-swappable layer is `ADR-013`'s boundary language, not a CRR/PDD requirement — CRR/PDD confirm only the one adopted provider/model pairing.
- **Target — context assembly:** Accepting the consumer-supplied context a conversation needs at start — for Onboarding, the worker's required-document/completeness state (`onboarding/MODULE_SPEC.md` §6.3 lines 149-150); Chatbot never initiates a conversation independent of a triggering consumer (`ADR-013` item 3).
- **Target — token/cost management:** A hard monthly token budget cap stored in config, a per-conversation token limit, a cached required-document list, and graceful fallback to a static checklist UI when limits are hit (CRR §8 line 109; PDD §4.14 line 151, §5.6 line 192 "Chatbot budget guard" job, §7.1 lines 267-268, §11 line 442). Chatbot owns the guardrail/decision to trigger fallback; the consumer only reacts to the signal (`ADR-013` item 3; `onboarding/MODULE_SPEC.md` §16.1).
- **Target — guardrails:** Transport (TLS in transit, not end-to-end encrypted) and input-validation/injection-defense guardrails for the conversation itself, including accepted-upload-type enforcement as a conversation-level guardrail (`onboarding/MODULE_SPEC.md:325`; PDD §5.2; `ADR-013`) — see `OD-CHAT-007` for a disclosed tension with Documents' own storage-layer file-type validation (`RULE-DOC-09`).
- **Target — AI audit:** Conversation-level logging (start/end, fallback triggers) for compliance and dispute resolution, consistent with the platform's general audit-log mandate (CRR §30) and `onboarding/MODULE_SPEC.md:360`'s reference to "Chatbot conversation started/ended (timestamp, [OPEN] conversation transcript retention)".
- **Target — secondary use (forward-looking, Compliance-owned workflow, Chatbot-executed):** The same agent is reused for GDPR subject-rights (data access/export) requests (CRR §8 line 110; CRR §26 line 343). `docs/03-modules/compliance/` holds only `.gitkeep` — no Compliance module specification exists yet to confirm this consumption contract from the other side; this is recorded here as a one-sided boundary assertion (mirrors `docs/03-modules/documents/MODULE_SPEC.md`'s `OD-DOC-012` treatment of its own Compliance-forward-looking edge).
- **Target — tool execution / conversation memory:** Named by `ADR-013` as owned responsibility classes; CRR/PDD confirm no concrete tool call and no explicit memory/persistence model — see `OD-CHAT-002`, `OD-CHAT-003`, `OD-CHAT-008`.

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6)

- **The onboarding business workflow itself** — onboarding state and its transitions, onboarding steps (Personalfragebogen, document-collection *orchestration decision-making*, contract-signing coordination, pool/claim, hire approval), onboarding-specific validation, onboarding completion signaling, and onboarding's own business rules are owned by Onboarding (`docs/03-modules/onboarding/MODULE_SPEC.md`). Onboarding triggers a Chatbot conversation and reacts to its outcome; it does not implement, configure, or operate the agent (`ADR-013` items 2-3).
- **Document storage** — document lifecycle, metadata, upload mechanism, storage abstraction (S3 EU), version history, categories, permissions, access, retrieval, and archival are owned by Documents (`backend-documents`, `SPEC-DOCUMENTS-001`). Documents' own specification independently frames Chatbot as "a distinct capability... Documents is the storage/retrieval target the chatbot's document-collection flow writes to and reads from, not the chatbot itself" (`documents/MODULE_SPEC.md:34`) — consistent with, not contradicting, this module's boundary. Whether Chatbot's own (unconfirmed) tool-execution surface ever calls Documents' upload interface directly, versus file upload being an entirely separate non-conversational UI action, is disclosed as open, not resolved, at `OD-CHAT-003`.
- **The GDPR subject-rights workflow and fulfilment ownership** — request intake, response assembly, and delivery to the data subject are conceptually owned by Compliance (CRR §8 line 110, §26 line 343); Chatbot only executes the conversation Compliance's workflow triggers (`ADR-013` item 3). No Compliance specification exists yet (`docs/03-modules/compliance/` holds only `.gitkeep`).
- **Employee/account lifecycle and activation** — whether an onboarding account activates is Onboarding/Employee-Management's decision, not this module's; Chatbot emits a completion/fallback signal only (`onboarding/MODULE_SPEC.md:150`; `ADR-013`).
- **Contract lifecycle** — owned by `backend-hr`/`SPEC-HR-001` per `ADR-012`; unrelated to this module.
- **Retention-sweep execution, consent governance, special-category field-governance policy** — conceptually Compliance's, unrelated to this module beyond disclosing which retention tier Chatbot's own records fall under, where determinable (`OD-CHAT-019`).

**Non-goals:** (confirmed out of the platform entirely, or explicitly excluded by CRR/PDD)

- Any marketplace-era concept — none existed in the marketplace-era data model and none is reintroduced here.
- Background checks, account lockout, login rate-limiting, CAPTCHA — explicitly excluded platform-wide (CRR §2 lines 32-35, §3 line 39); **not** to be conflated with the separate, unresolved question of a conversation-level cost/abuse-prevention control for this module's own token-metered endpoint (`OD-CHAT-010`).
- Payroll computation of any kind (CRR §23) — unrelated to this module.
- Qualified Electronic Signature (QES) / e-signature integration — unrelated to this module (CRR §9 lines 118-119).

## State and Lifecycle

**Current:** No state exists. No `ChatbotConversation`/any-name model, no lifecycle, no states, no transitions are implemented anywhere in the repository.

**Target lifecycle (reasoned from the confirmed capability boundary and CRR/PDD; states beyond entry/completion/fallback are not explicitly enumerated by either authority — labelled open, not assumed):**

- **Entry:** A conversation is created when a consumer (Onboarding today; Compliance, forward-looking) calls `IF-CHATBOT-StartConversation`, supplying worker id, purpose, and context (CRR §8 lines 103-110; `onboarding/MODULE_SPEC.md` §6.3).

- **Retention/persistence:** whether conversation transcripts are persisted beyond conversation completion, and whether engaging the chatbot requires explicit data-processing consent, is genuinely unresolved. This is the **same open question** already recorded as Onboarding's own `OPQ-3`, which itself states resolution ownership sits with this module ("This is a Chatbot-module (`backend-chatbot`) decision per `ADR-013`"); recorded here as `OD-CHAT-008`, cross-referencing Onboarding's `OPQ-3` rather than duplicating it as an independently-discovered gap.
- **Concurrency:** Unaddressed by CRR/PDD for this capability — labelled unknown (`OD-CHAT-016`), consistent with the identical gap already recorded for `backend-hr` (`OD-HR-08`) and Documents (`OD-DOC-011`).

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:** Not evaluable for current state (nothing is implemented). Target: a monthly-cap or per-conversation-limit breach triggers the confirmed graceful fallback (`RULE-CHAT-03`); whether a raw Claude API outage (distinct from budget exhaustion) triggers the identical path, and what retry/backoff policy applies, is unspecified by CRR/PDD (`OD-CHAT-012`, `OD-CHAT-015`).

**Trust boundaries/authorization:** Current: no route exists; nothing to evaluate. Target: every worker-facing conversation-turn/status call MUST bind to the authenticated actor's own identity — a conversation id or worker id MUST NOT be accepted as a bare, unverified client-supplied parameter (`RULE-CHAT-09`, `REQ-CHAT-013`). Broader document-level-style RBAC/permission granularity (who besides the owning worker — a manager, an auditor, or Compliance for a subject-rights request — may access a conversation or its outcome) is **not specified anywhere in CRR/PDD**, mirroring `documents/MODULE_SPEC.md`'s `OD-DOC-005`/`OD-DOC-007` treatment — elevated here to **blocks G2 Specification Freeze** (`OD-CHAT-005`), given this module handles sensitive personal data and, for its secondary use, GDPR-subject-rights-adjacent content. Whether the worker's mobile client talks to a Chatbot-owned end-user-facing API surface directly, or Onboarding proxies every turn, is separately unresolved (`OD-CHAT-004`) and materially affects the shape of this trust boundary.

**Data classification/retention:** Conversation content is personal data at minimum (identity information, document references, worker-supplied text) and, for the subject-rights secondary use, may carry the full content of a GDPR export request. TLS-in-transit applies; not end-to-end encrypted (`RULE-CHAT-07`, restating — not newly deriving — the same in-transit expectation `onboarding/MODULE_SPEC.md:325` states for its own transmission leg). Encryption-at-rest for any persisted conversation content is unaddressed and contingent on `OD-CHAT-008` resolving toward persistence (`OD-CHAT-018`, mirroring `documents/MODULE_SPEC.md` `OD-DOC-017`). Retention-tier assignment (which of CRR §25's three automatic-deletion tiers applies to conversation-adjacent records) is unresolved (`OD-CHAT-019`, mirroring `OD-DOC-001`/`OD-HR-11`). Whether worker conversation content could ever incidentally intersect CRR §27's special-category fields (Konfession, disability, health) is unconfirmed — no CRR/PDD statement addresses conversational content specifically, distinct from the document *types* Documents already tracks as open (`documents/MODULE_SPEC.md` `OD-DOC-002`).

**Performance budgets/workload:** No explicit SLO is defined in CRR/PDD for conversation-turn latency. Design intent: the confirmed token caps (monthly + per-conversation, `RULE-CHAT-03`) function as a cost-bound control, not a latency SLO. Concrete latency/throughput budgets are deferred to implementation and not asserted here (Constitution §6). Once a `ChatbotConversation` schema exists, queries by worker id (+ purpose/status) should be indexed at schema-creation time, mirroring the platform-wide missing-compound-index finding already recorded for Documents (`OD-DOC-019`) and Quality (`FIND-PERF-003`) — forward-looking, not yet exercised (`OD-CHAT-020`).

**Observability/audit:** No audit behaviour is implemented (nothing exists). Target: conversation-level audit-log entries for start/completion/fallback (`RULE-CHAT-10`, `REQ-CHAT-014`), consistent with the platform's shared `AuditLog` pattern (`base-service.ts`) and CRR §30's general mandate. Full transcript-content logging/retention is a separate, still-open question (`OD-CHAT-008`).

**AI-specific guardrail note (new to this module's capability class):** Prompt-injection resistance — a risk class specific to LLM-backed agents, distinct from the generic "injection defense" `onboarding/MODULE_SPEC.md:325` attributes to this module's conversation guardrails — is not addressed by any CRR/PDD or cross-spec source. This is flagged as a new, non-fabricated concern (`OD-CHAT-006`), analogous to how `documents/MODULE_SPEC.md`/`hr/MODULE_SPEC.md` flag malware/content-scanning as a deferred-not-silent position (`OD-DOC-016`/`OD-HR-14`) rather than leaving it unaddressed.

**Abuse-prevention note:** CRR §2 confirms **no login rate-limiting** platform-wide (CRR §2 line 34) — but this is distinct from the unresolved question of whether a conversation-level rate-limit/abuse-prevention control applies to this module's own cost-incurring endpoint(s) (each conversational turn spends real LLM tokens); the two must not be conflated (`OD-CHAT-010`).
