## Purpose and Scope

**Outcome:** Establish Retention as the single, standalone bounded context owning the generic three-tier GDPR data-retention **mechanism** — the tier-classification model, the `RetentionLog` entity, the daily automatic-deletion sweep job (schedule, execution, and audit logging of deletions performed) — and expose an `IF-RETENTION-*` interface family through which every consuming module registers/tags its own record types into a tier and queries deletion eligibility, so that no other module builds a competing sweep job, deletion scheduler, or tier-policy engine of its own (CRR §25; PDD §9.3, §9.4, line 402; PDD §10 Phase 3/M4).

**In scope:**

- **The generic three-tier retention classification model** (CRR §25, lines 333-338): Tier 1 — shift clock-in/out coordinates, 6 months then hard delete; Tier 2 — general personal/profile data, 5 years; Tier 3 — payroll/tax-adjacent fields (IBAN, tax ID, payslip-request records, wage records), 6 years (per §41 EStG / §257 HGB / §147 AO). This module owns the tier definitions, their retention windows, and the reusable classification model other modules' record types are tagged into — not the per-field assignment decision itself for any *other* module's data (see Out of scope).
- **The `RetentionLog` entity** (PDD §9.3, line 392: "Tracks deletion eligibility per data category") — the target-state persisted record of which data category/tier a tagged record belongs to and its computed deletion-eligibility state.
- **The daily automatic-deletion sweep job** (CRR §25, line 336: "All deletion is AUTOMATIC (scheduled jobs), not manual"; PDD §9.4, line 402: "Coordinates, payroll/tax fields, and general PII tagged by retention category for the sweep job"; PDD §7-adjacent scheduled-jobs infra, node-cron/BullMQ on Redis, PDD line ~165; PDD "Retention sweep | Daily" table entry, line ~188): the mechanism, schedule (daily), and execution logic that identifies eligible records via tagged retention category and hard-deletes them once their tier's window has elapsed.
- **`IF-RETENTION-*` interfaces** (naming consistent with this repository's `IF-CONSENT-*`/`IF-HR-*` convention) exposed to every consuming module for (a) registering/tagging a record type or individual record into a tier, and (b) querying deletion eligibility/status for a given record or record type. This module supplies the mechanism and the interface; it does not itself decide which table/column in any other module holds which tier's data (see Out of scope).
- **Audit logging of deletions performed** by the sweep job, consistent with the platform-wide "every important action is logged, immutably" mandate (CRR §30) — recording what was deleted, under which tier, and when, without retaining the deleted personal data itself.

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6)

- **Which specific table/column in each consuming module holds which tier of data.** This remains each consuming module's own open decision, tracked in that module's own specification and the corresponding Specification Issues Register entry: `SIR-NOTIF-002` (Notification), `SIR-ATT-009`/`SIR-ATT-011` (Attendance), `SIR-AUTH-011` (Auth: `User`/`Session`/`AuditLog`), `SIR-HR-017`/`OD-HR-11` (HR: contract document), `SIR-DOC-001`/`OD-DOC-001` (Documents), `SIR-CHAT-017`/`OD-CHAT-019` (Chatbot), `SIR-CONSENT-003`/`OD-CONSENT-003` (Consent). Retention supplies the mechanism and the interface (`IF-RETENTION-RegisterCategory`/`IF-RETENTION-TagRecord`); the consuming module supplies the classification of its own fields by calling that interface once its own open decision is resolved.
- **Whether the 6-month coordinate retention/hard-deletion job — and the coordinate columns themselves — is owned by `backend-attendance` or `backend-geo`.** This is `SIR-GEO-002`/`OD-GEO-002`, a real, currently-open boundary question between those two modules. This specification states only that Retention owns the generic sweep MECHANISM/schedule/execution across all tiers, including Tier 1; it does **not** resolve, and explicitly does not attempt to resolve, which of Attendance or Geo is the upstream data owner/writer that registers the Tier-1 coordinate record type with Retention. That determination remains `SIR-GEO-002`'s own open item, to be resolved by Attendance/Geo, not by this module.
- **Compliance's broader subject-rights/governance orchestration** (CRR §26: subject-rights access/export requests, handled automatically via a button or the chatbot; data minimization not actively pruned but each field tied to a stated legal basis) — `docs/03-modules/compliance/` holds only `.gitkeep`; no `MODULE_SPEC.md` exists there. This module's sweep-execution and deletion-audit surface is a candidate input to a future Compliance module's governance/reporting needs, referenced here as a related-but-undefined capability, not claimed or scoped by this specification (mirrors `SIR-DOC-012`/`OD-DOC-012`'s identical one-sided-boundary framing for the Documents/Compliance relationship).
- **Special-category data handling** (Konfession, disability, health data; CRR §27's restricted-visibility mechanism and per-access audit-entry requirement) — this module's sweep job may eventually delete special-category fields once tagged into a tier by their owning module, but the *handling* (visibility restriction, per-view audit granularity) of that data while it exists is the owning module's concern, not this module's.
- **Any per-module retention-classification decision this specification cannot make on another module's behalf** — see the full list of inherited open items above and in Risks, Assumptions, and Open Decisions.

**Non-goals:** (confirmed out of scope entirely, or explicitly excluded by CRR/PDD)

- Manual/ad-hoc deletion tooling or an admin-facing deletion UI — CRR §25 confirms all deletion is automatic via scheduled jobs, not manual; CRR §30 confirms no admin-facing log-viewer screen exists platform-wide, and this module introduces neither.
- Data minimization/pruning of collected fields ahead of a record's tier window elapsing — CRR §26 confirms "we don't need minimization," though each field must remain tied to a stated legal basis (a Compliance-governed concern, not this module's).
- Soft-delete, archival, or "cold storage" retention beyond each tier's stated window — CRR §25 states hard delete for Tier 1 and implies the same automatic-deletion posture for Tiers 2 and 3; no CRR/PDD text describes an intermediate archival state, and none is invented here.
- Any second, competing sweep job, deletion scheduler, or tier-policy engine inside any other module — explicitly and permanently excluded by this module's exclusive-ownership claim (see Ownership and Boundaries), consistent with the G1.5 Boundary Collision check finding no other module claims this ownership today.

## Actors and Terminology

| Term/actor | Canonical definition | Source |
|---|---|---|
| Retention tier | One of three CRR §25-confirmed data-retention classes, each with its own window and deletion trigger: Tier 1 (shift coordinates, 6 months), Tier 2 (general personal/profile data, 5 years), Tier 3 (payroll/tax-adjacent fields, 6 years) | CRR §25 |
| Retention category / data category | The consuming-module-specific record type or field group tagged into a tier (e.g., "shift clock-in coordinate," "worker profile field," "payslip-request record") — the unit `RetentionLog` tracks deletion eligibility for | PDD §9.3 (line 392), §9.4 (line 402) |
| `RetentionLog` | The target-state entity tracking deletion eligibility per data category; this module's owned persisted state | PDD §9.3 (line 392) |

| Deletion eligibility | The computed state of whether a specific tagged record has exceeded its tier's retention window and is due for hard deletion by the next sweep run | PDD §9.3 (line 392) |
| Hard delete | Permanent, non-recoverable removal of a record's data, as distinct from soft-delete/archival (CRR §25 states hard delete explicitly for Tier 1; the same automatic-deletion posture is read consistently across all three tiers, no archival state being named anywhere in CRR/PDD) | CRR §25 (line 333) |
| Consuming module | Any module (Notifications, Attendance, Auth, HR, Documents, Chatbot, Consent, Geo, and any future module holding personal data) that registers/tags its own record types with this module and relies on the sweep job for automatic deletion, without itself building a competing mechanism | This specification (Ownership and Boundaries) |
| Tax advisor sign-off | The client-side action item (CRR §25 `[ACTION]`) requiring the client's tax advisor to confirm the retention-tier mapping before final lock-in; an open item this module records but cannot itself resolve | CRR §25 (line 338) |
| Compliance | A related-but-undefined future capability (`docs/03-modules/compliance/` holds only `.gitkeep`) that may consume this module's deletion-audit surface for subject-rights/governance purposes; not scoped or claimed by this specification | CRR §26; Out of scope |

## Business Rules

| Rule | Preconditions | Outcome/invariant | Exceptions/precedence | Owner/source |
|---|---|---|---|---|
| `RULE-RETENTION-01` | Any consuming module or this module's own sweep logic references a retention tier | Only the three CRR §25-confirmed tiers (1/2/3) with their stated windows (6mo/5yr/6yr) exist; no other tier or window is used | None — closed set, confirmed by CRR §25 | This module (CRR §25) |
| `RULE-RETENTION-02` | A consuming module has a record type/field it needs deleted per GDPR policy | It registers/tags that category with this module via `IF-RETENTION-RegisterCategory`, supplying its own tier assignment | This module never infers the assignment; an unregistered category is never swept (see `RULE-RETENTION-07`) | This module (mechanism); consuming module (classification) — PDD §9.4 (line 402) |

## Ownership and Boundaries

**Module owner:** `unassigned` — accountable owner assignment is reserved human authority (`SYNC-001`; no `CODEOWNERS`, empty `backend/package.json` author, consistent with every other module in this repository). Code-level home is the target `backend-retention` module (`backend/src/modules/retention`), which does not exist today in any form — not a stub, not a `.placeholder` file. This specification is the proposed docs↔code mapping for `backend-retention`; it is not asserted as final until G2 freeze.

**Owned state:**

- The three-tier definitions (identifier, window, deletion trigger) — the canonical tier catalog CRR §25 confirms.
- `RetentionLog`: the registered category-to-tier mapping table, and the deletion-eligibility state computed per registered category/record.
- The daily sweep job's own execution state (last-run timestamp, run status) — target-state, no CRR/PDD-confirmed schema shape beyond "tracks deletion eligibility per data category" (PDD §9.3).
- The immutable deletion-audit log entries this module writes when the sweep performs a deletion.

**Consumed state (owned elsewhere, referenced, never redefined):** every consuming module's own record data that is registered/tagged into a tier — this module never owns, duplicates, or redefines the underlying business record (e.g., a shift-coordinate row, a consent record, a document row); it owns only the tier-mapping metadata and the deletion-execution act itself. The authenticated caller/service context of any module invoking `IF-RETENTION-*` (Authentication/User Management) is likewise consumed, never redefined.

**Permitted writes:** only to this module's owned state above (tier catalog, `RetentionLog` mappings/eligibility state, sweep-run state, deletion-audit log), and only through its own interfaces or its own scheduled sweep execution. This module's sweep job performs the *delete* operation against a consuming module's own data store on that module's behalf, per the registered category — this is a delegated execution permission, explicitly granted by the act of registration (`RULE-RETENTION-02`), not a general write permission into another module's domain state. This module never creates, updates, or otherwise mutates a consuming module's business record other than executing the confirmed hard-delete once eligibility is reached.

**Boundary/non-responsibilities:** this module does not decide which table/column in any other module holds which tier of data (`RULE-RETENTION-07`); does not resolve the Attendance/Geo Tier-1 coordinate-ownership question (`SIR-GEO-002`/`OD-GEO-002`, `RULE-RETENTION-08`); does not perform subject-rights access/export orchestration, data-minimization policy, or broader compliance governance (Compliance's undefined future role, CRR §26); does not perform authentication, session management, or RBAC/scope enforcement itself; does not classify special-category data (CRR §27) beyond deleting it once tagged by its owning module. Per the G1.5 Boundary Collision check performed before authoring, no other module today claims ownership of retention-tier deletion execution, the `RetentionLog` entity, or a tier-policy engine — this is a settled, non-competing boundary at the time of authoring, subject to the same G4 architecture/dependency review any other candidate spec undergoes before freeze.

## State and Lifecycle

**States (retention-record-level, owned here):**

- **Unregistered** — a consuming module's record type/field exists but has not been registered with this module via `IF-RETENTION-RegisterCategory`; not swept, not tracked in `RetentionLog` (default state of every consuming module's data absent explicit registration — this is the current state of every module's own data today, per the inherited open items listed in Evidence and Traceability).
- **Registered** — a category has been declared with a tier assignment; `RetentionLog` now tracks it, but individual record instances may or may not yet be tagged (granularity `[OPEN]`, `OD-RETENTION-04`).
- **Tagged / Tracked** — a specific record (or the category as a whole, depending on the resolved granularity) has a computed retention window start point and is being tracked for eligibility.
- **Eligible** — the tracked record/category has exceeded its tier's window as of the current date; awaiting the next daily sweep run.
- **Deleted** — the sweep has executed the hard delete; an immutable deletion-audit entry exists; the underlying record no longer exists in its owning module's data store.

**Transitions:**

- `Unregistered → Registered` — a consuming module calls `IF-RETENTION-RegisterCategory` with a tier assignment (`RULE-RETENTION-02`).
- `Registered → Tagged/Tracked` — a consuming module calls `IF-RETENTION-TagRecord` (or, per the unresolved granularity question, the sweep itself queries an already-registered category by an existing timestamp column — `OD-RETENTION-04`).
- `Tagged/Tracked → Eligible` — time passes and the record/category's tier window elapses (`RULE-RETENTION-03`).
- `Eligible → Deleted` — the daily sweep executes (`RULE-RETENTION-04`, `RULE-RETENTION-05`), producing a deletion-audit entry (`RULE-RETENTION-06`).

**Invariants:** no record is ever deleted by this module's sweep unless it is in the `Eligible` state, which itself requires prior `Registered`/`Tagged` state (`RULE-RETENTION-07` — unregistered data is never swept); a deletion is never performed without a corresponding immutable audit-log entry (`RULE-RETENTION-06`); no tier or window other than the three CRR §25-confirmed values is ever applied (`RULE-RETENTION-01`).

**Concurrency:** not addressed in the authoritative documents for this module specifically; labelled unknown (Constitution §6, `OD-RETENTION-07`) — e.g., whether the daily sweep run is safe to overlap with a concurrent registration/tagging call from a consuming module, or whether two sweep runs could ever overlap (job-scheduler-level exactly-once semantics), is unresolved.

**Retention/migration:** this module's own owned state (`RetentionLog`, sweep-run state, deletion-audit log) has no CRR/PDD-confirmed retention tier of its own — the deletion-audit log arguably should itself never be deleted (mirroring CRR §30's "every important action is logged" mandate with no stated expiry for audit logs generally, distinct from the 5-year figure CRR §30 states for that platform-wide audit log specifically) — see `OD-RETENTION-08`. No prior `RetentionLog` data exists in the current schema to migrate; this is entirely net-new capability, built pre-launch with no production data (PDD §10 pattern, mirrored from every other net-new module in this repository).

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:**

- A consuming module never registers a data category → that data is silently never swept; this is the *current, confirmed* state of at least seven consuming modules' own data today (the inherited `SIR-*` items listed throughout this specification) and is not a failure of this module's own mechanism, but a real, immediate compliance-effectiveness gap this specification cannot close unilaterally.
- The daily sweep job fails to run on a given day (scheduler outage, deploy window, etc.) → no confirmed catch-up/backfill behavior exists in CRR/PDD; labelled unknown — `[OPEN]`, `OD-RETENTION-02`.
- A consuming module's own delete execution (triggered by this module's sweep, per the delegated-execution model in Ownership and Boundaries) fails partway through → no confirmed partial-failure/retry/idempotency behavior exists in CRR/PDD; labelled unknown — `[OPEN]`, `OD-RETENTION-09`.
- Current-state: this module does not exist in code; every interface listed above is target-state only.

**Trust boundaries/authorization:** every `IF-RETENTION-*` interface's calling-module-identity parameter MUST be derived from the calling module's own already-authenticated service/session context — never accepted as an unverified client-supplied field — mirroring the precedent set by `docs/03-modules/hr/MODULE_SPEC.md`'s `RULE-HR-14`/`FIND-SEC-HR-02` and `docs/03-modules/consent/MODULE_SPEC.md`'s identical treatment of its own `IF-CONSENT-*` family. `IF-RETENTION-RegisterCategory`/`IF-RETENTION-TagRecord` are invoked by a consuming module's own trusted backend logic only, never by an end-user-facing caller. `IF-RETENTION-GetDeletionAuditLog` is exposed to Compliance as a read-only surface only, once a Compliance module exists — no write path is defined for that consumer role by design. **Security gap, disclosed not silently accepted:** the "Admin" caller class named in the interface table has no defined RBAC scope, role model, or authorization boundary anywhere in this specification — mirroring `docs/03-modules/consent/MODULE_SPEC.md`'s `OD-CONSENT-011` finding for its own equivalent interface. Until `OD-RETENTION-05` is resolved with an explicit permission/scope definition, **no implementation may grant "Admin" read access to `IF-RETENTION-GetDeletionAuditLog`**. Separately, because this module's sweep job performs cross-module hard-delete execution, its own internal authorization to call into each consuming module's delete mechanism is itself unspecified by CRR/PDD — `[OPEN]`, `OD-RETENTION-10`.

**Data classification/retention:** Germany-only, consistent with every other module in this platform; no data leaves the EU/EEA. This module's own owned state (`RetentionLog` mappings, sweep-run state) is metadata about other modules' personal data, not the personal data itself; the deletion-audit log records category/tier/timestamp only, explicitly never the deleted personal data (`RULE-RETENTION-06`) — this is a deliberate design constraint to avoid this module itself becoming an un-retained copy of the very data it deletes elsewhere. The retention tiers this module executes are themselves confirmed (CRR §25); the tax-advisor sign-off action item (CRR §25, line 338) remains an open precondition to final lock-in of the tier-mapping's legal correctness — tracked as `OD-RETENTION-01`, not resolvable by this specification.

**Performance budgets/workload:** no explicit SLO is defined in the authoritative documents (mirrors `SIR-ATT-009`'s identical finding for the retention-sweep window specifically, and `SIR-DOC-019(b)`'s O(n)-rescan risk against `WorkerDocument` rows once Documents registers). Design intent, not a confirmed budget: the daily sweep must scan across every registered category's tagged/tracked records to compute eligibility, which — absent an indexed, bounded query design per category (e.g., an indexed timestamp column with a `WHERE created_at < now() - interval` predicate, rather than a full-table rescan) — risks the same class of unbounded-scan performance issue independently flagged for `backend-quality` (`SIR-QUAL-008`) and anticipated for `backend-documents` (`SIR-DOC-019(b)`) once that module registers. This is recorded here as a required implementation-time design constraint, not assumed satisfied — `[OPEN]`, `OD-RETENTION-11`.

**Observability/audit:** every deletion performed by the sweep must be logged immutably, recording category/tier/timestamp only (never the deleted personal data), consistent with CRR §30's "every important action is logged" mandate. The sweep's own run completion (success/failure, count deleted per category) should likewise be observable, though no CRR/PDD-confirmed mechanism for this (e.g., an operational dashboard) exists — labelled unknown, `OD-RETENTION-12`. No admin-facing log-viewer screen exists platform-wide (CRR §30) and this module does not introduce one.

## Rollout and Compatibility

This module is entirely net-new capability within the marketplace → Workforce Operations Platform forward refactor (PDD §10, Phase 3 "Compliance & onboarding," Milestone M4 — alongside Personalfragebogen, chatbot, consent gate, contract storage, and payslip request; M4 validation explicitly names "Retention sweep + consent tests"). It is pre-launch with no production data requiring retroactive tier assignment, so no dual-run migration is needed (PDD §10). Sequencing: this module's mechanism can be built independent of any single consuming module's own registration readiness, but its practical effectiveness is gated on each consuming module resolving its own open tier-assignment decision (the `SIR-*` items listed throughout this specification) and calling `IF-RETENTION-RegisterCategory` — a cross-module rollout dependency this specification records but does not control.

**Feature flags:** the sweep job itself would sit behind the existing `FEATURE_*` env-flag convention, consistent with every other net-new module — noting that `SIR-NOTIF-003`/`SIR-DOC-013`/`SIR-CRM-014`/`SIR-AUTH-012` already record that no such convention actually exists in the codebase today despite PDD §10's claim; this module inherits that same platform-wide factual gap rather than resolving it (`OD-RETENTION-13`).

**Backward compatibility:** not applicable — no current-state code, route, or schema exists to preserve or break.

**Rollback:** because this is additive, pre-launch work, rollback would be disabling the sweep job's scheduled trigger and redeploying without registration/execution wired in; any already-registered categories would simply stop being swept until re-enabled, with no data-loss risk from the rollback itself (only continued non-deletion, which is the pre-launch baseline state today).

**Removal criteria:** not applicable — the three-tier automatic-deletion sweep is a confirmed, permanently-owned legal/compliance capability (CRR §25); it is not a removable/sunset-able feature.
