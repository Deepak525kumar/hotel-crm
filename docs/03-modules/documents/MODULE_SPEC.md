## Purpose and Scope

**Outcome:** Establish Documents as the single, implementation-independent capability owning document lifecycle, document metadata, uploads, storage abstraction, version history, file status, document categories, document permissions, document access, document retrieval, document archival, and document relationships for every worker-facing and manager-facing document in the platform (uploaded onboarding documents, non-EU work-permit documents, and the scanned hand-signed employment contract as a **mechanism-class consumer**, per `RULE-HR-11`) — so that Onboarding, `backend-hr` (Contracts), Employee Management, and (forward-looking) Payslips/Compliance can reference one owner instead of each independently defining upload/storage behaviour. S3 (EU) object storage is implementation detail this capability owns operationally, not a capability it is defined by (CRR §4 line 53; CRR §7 lines 94–99; PDD §5.2 line 164, §5.7 line 195, §9.3 line 389).

**In scope:**

- **Current:** Nothing is implemented as a Documents capability. `backend/src/modules/documents` does not exist (directory `docs/03-modules/documents/` held only `.gitkeep` prior to this document). The single document-adjacent surface in the codebase — `POST /workers/:worker_id/documents` inside `backend/src/modules/hr/` — is recorded here **only as current-state evidence of the missing capability and of architectural debt** (see Evidence and Traceability, Migration Gaps `MIG-GAP-DOC-001`); it is not, and does not become, part of this module's owned surface, because it physically lives inside, and is scoped by, `backend-hr` (`SPEC-HR-001`), which explicitly disclaims owning the general capability (`docs/03-modules/hr/MODULE_SPEC.md:43,141` — "Documents (conceptual) owns general capability").
- **Target:** Document upload with expiry tracking at account creation (CRR §4 line 53). Worker upload of all required documents in the app during onboarding (CRR §7 line 96). Work-permit/residence document requirement restricted to non-EU/EEA/Swiss workers, with EU/EEA/Swiss citizens exempt (CRR §7 lines 97–98). Storage of all documents in S3, EU region, with no data leaving the EU/EEA (PDD §5.2 line 164; §5.7 line 195; §14 line 489). The `WorkerDocument` data model: "Uploaded docs + expiry; work-permit (non-EU only)" (PDD §9.3 line 389) — the sole target-state entity name CRR/PDD assign to this capability; there is no separate "Document" model in either authority.
- **Target (mechanism-class consumer relationship, not owned execution):** Serving as the storage/retrieval mechanism the contract-scan upload (`backend-hr`, `RULE-HR-11`) and the onboarding document-collection chatbot (Onboarding, CRR §8) both ride on, without Documents owning contract lifecycle (ADR-012) or onboarding orchestration (Onboarding's own workflow behaviour).

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6)

- **Contracts** — the entire contract-lifecycle/template/generation/metadata/version/amendment/signature/manager-confirmation/renewal/expiry/archival surface is owned by `backend-hr`/`SPEC-HR-001` per `ADR-012` (Accepted, 2026-07-12; `docs/14-governance/architecture-decisions/ADR-012-contracts-ownership-hr-bounded-context.md`). Documents is named there explicitly as a **consumer**, not an owner, of Contracts (ADR-012 Decision item 3: "Onboarding, Employee Management, Documents, Payslips, Compliance... consume this functionality through `backend-hr`'s interfaces; they do not own it"). The scanned signed contract is *mechanically* uploaded like any other document (CRR §9 line 132) — that mechanism-sharing does not transfer contract ownership to Documents.
- **Payslips** — the payslip-request-to-manager-email flow (CRR §23) is owned by `backend-hr`/`SPEC-HR-001` (`docs/03-modules/hr/MODULE_SPEC.md:32`); `docs/03-modules/payslips/` holds only `.gitkeep` (no standalone module exists or is proposed here).
- **HR / employee records** — employee identity, core employment fields, lifecycle status, skill tags, and the profile-and-history view are owned by Employee Management (`docs/03-modules/employee-management/MODULE_SPEC.md`, `SPEC-EMP-001`), which explicitly lists "Document storage, expiry tracking, and the non-EU work-permit requirement" as attributed to the Documents module and out of its own scope (`SPEC-EMP-001:39`, verbatim: "...(Documents module; CRR §4, §7)" — no definite article in source; corrected `FIND-CONS-DOC-006`).
- **Retention sweep execution** — the daily automatic tiered-retention deletion mechanism (schedule, execution, `RetentionLog`, deletion audit) is owned by `backend-retention`/`SPEC-RETENTION-001` (`docs/03-modules/retention/MODULE_SPEC.md`, G1.5 PASS). Documents classifies which retention tier its own records fall under (where determinable, `RULE-DOC-06`) and registers that classification through Retention's `IF-RETENTION-*` interfaces; it does not itself run the sweep or delete rows.
- **Compliance** — subject-rights access/export fulfilment orchestration and special-category field governance policy remain conceptually assigned to a Compliance capability (CRR §26, §27); `docs/03-modules/compliance/` holds only `.gitkeep`. Documents exposes retrieval of its own records for export; it does not orchestrate or fulfil subject-rights requests itself.
- **Consent** — the daily GDPR consent gate (CRR §24) is unrelated to document lifecycle; `docs/03-modules/consent/` holds only `.gitkeep`.
- **Chatbot** — the AI onboarding/subject-rights conversational agent (CRR §8, §26) is a distinct capability (`backend-chatbot`, currently a placeholder per PDD §2.2 line 44); Documents is the storage/retrieval target the chatbot's document-collection flow writes to and reads from, not the chatbot itself.
- **Geo** — geofencing/location capture (CRR/PDD §4.7, `backend-geo` placeholder) is unrelated.
- **CRM** — the Hotel/Hotel-Group reference record (`backend-crm`/`SPEC-CRM-001`, `ADR-011`) is unrelated; Documents does not scope by hotel beyond whatever hotel association a `WorkerDocument` inherits from its owning worker/employment record (undetermined — `OD-DOC-006`).
- **Onboarding orchestration** — the Personalfragebogen self-service form, the AI document-collection chatbot conversation flow, application→familiarization sequencing, and the pool/claim hire-approval mechanism are owned by Onboarding (`docs/03-modules/onboarding/MODULE_SPEC.md`), which itself explicitly disclaims owning document *validation*/*storage*: "Document validation itself is owned by the Documents module" (`onboarding/MODULE_SPEC.md:44`) and "Documents are stored by the Documents module; Onboarding maintains only references to them" (`onboarding/MODULE_SPEC.md:347`). Onboarding's own first-person claim to "document collection orchestration" (`onboarding/MODULE_SPEC.md:44,86`) is its own workflow-orchestration responsibility (deciding what to ask for and when, driving the chatbot conversation) — a consumer/dependency relationship with Documents, not a competing ownership claim over storage/lifecycle, and is recorded as such per the Lead Architect's G1.5 evidence.

**Non-goals:** (confirmed out of the platform entirely, or explicitly excluded by CRR/PDD)

- Any marketplace-era document/attachment concept — none existed in the marketplace-era data model (PDD §2.3 lines 45–56 list no document-bearing model) and none is reintroduced here.
- Certifications (formal, expiring qualifications) and certification-expiry reminders — explicitly excluded by CRR §4 (lines 54–55: "❌ No certifications... ❌ No certification expiry reminders"), a distinct concept from the confirmed general "document upload + expiry tracking" (CRR §4 line 53).
- Signature capture, signature authenticity verification, or automated detection that a document is signed — explicitly excluded for the contract-scan use case (CRR §9 line 139) and not requested for any other document type.
- Qualified Electronic Signature (QES) / e-signature provider integration of any kind (CRR §9 lines 118–119; PDD §11, Appendix).
- Payroll computation of any kind (CRR §23 lines 320–321) — Documents may store payroll-adjacent artifacts by reference (e.g., wage records classified Tier 3) but performs no computation.

## Requirements and Acceptance Criteria

`REQ-DOC-001` through `REQ-DOC-012` and `REQ-DOC-014` through `REQ-DOC-017` are all **Target** (confirmed authority, unbuilt). ## Ownership and Boundaries

**Module owner:** `unassigned` — reserved human authority (SYNC-001; `MODULE_REGISTRY.yaml:6-9`). No code module currently exists for this capability; the proposed registry id is `backend-documents` (see Proposed Knowledge Deltas) — **proposed, not registered**.

**Owned state:**

- **Current:** None. No `Document`/`WorkerDocument` Prisma model exists (grep-confirmed against `backend/prisma/schema.prisma`); this capability holds zero business state today.
- **Target (proposed, unowned until a human/architecture decision assigns `backend-documents` and ratifies the state-domain):** `WorkerDocument` — uploaded-document reference (S3 EU key/URL), expiry, work-permit indicator (non-EU only), and (unspecified by CRR/PDD, open) whatever version/category/permission/status/archival/relationship fields the migration gaps below name.

**Consumed state (owned elsewhere, referenced never redefined):**

- Worker nationality — sourced from Onboarding's Personalfragebogen data (owner: Onboarding capability; concrete model `PersonalData`, PDD §9.3 line 388) — read-only, to compute the work-permit-required branch (`RULE-DOC-03`).
- The employment/worker identity a `WorkerDocument` attaches to — owned by Employee Management / the `User`/`HotelWorker` state domains (`DEPENDENCY_GRAPH.yaml:63,66`) — read-only, as a foreign key target.

**Permitted writes (target only; none current):** `WorkerDocument` rows and their own audit trail entries (via the shared `BaseService.logAudit` pattern every other module uses, `base-service.ts`). This module would never write Contract (backend-hr), User/HotelWorker/employment-status, Personalfragebogen, consent, or retention-execution state.

**Boundary/non-responsibilities:**

- This module does **not** own contract lifecycle (`backend-hr`/`SPEC-HR-001`, `ADR-012`), payslips (`backend-hr`), employee identity/lifecycle status (`SPEC-EMP-001`), onboarding orchestration/chatbot conversation flow (Onboarding), retention-sweep execution (`backend-retention`/`SPEC-RETENTION-001`), subject-rights fulfilment (Compliance, conceptual), consent (Consent, conceptual), or hotel scoping (`backend-crm`).
- **Ownership challenge (Boundary Loop) — for every state below, owner/readers/writers/consumers are proven or escalated:**
  - `WorkerDocument` (target) — Owner: **proposed** `backend-documents`, unratified. Writers (target): `backend-documents` only, once it exists. Readers (target, inbound consumer edges): Onboarding (completeness/collection orchestration), `backend-hr` (contract-scan mechanism consumer per `RULE-DOC-04`, and today the physical host of the stub — see `MIG-GAP-DOC-001`), Employee Management (activation-gate read per `SPEC-EMP-001:197`). Consumers (forward-looking, no `MODULE_SPEC.md` exists yet): Payslips, Compliance. **Not proven** — no state-domain id exists yet in `DEPENDENCY_GRAPH.yaml` (`OD-DOC-004`); this is a proposed ownership assertion pending a human/architecture ratification, exactly like `OD-CRM-01`'s Hotel Group entity was left unproven pending decision.
  - The **physical stub location** (`POST /workers/:worker_id/documents` inside `backend-hr`) is a confirmed instance of **architectural debt, not a boundary collision**: `backend-hr`'s own specification (`SPEC-HR-001`) already discloses that it does not own the general capability and that the mechanism should conceptually belong to Documents (`hr/MODULE_SPEC.md:43,141`, `RULE-HR-11`). No module claims to *own* general document lifecycle/storage today; this specification is the first to claim it, consistent with the G1.5 Boundary Collision Gate `PASS` already recorded by the Lead Architect. Migrating the stub's physical code location from `backend-hr` to a real `backend-documents` module is `MIG-GAP-DOC-001`, a human/architecture-scheduled refactor, not a same-session action of this document.
  - **Onboarding's "document collection orchestration"** claim (`onboarding/MODULE_SPEC.md:44,86`) is independently distinguished from Documents' storage/validation ownership by that same specification's own text (`onboarding/MODULE_SPEC.md:44`: "document validation itself is owned by the Documents module"; `:347`: "Documents are stored by the Documents module; Onboarding maintains only references to them"). This is recorded as a **consumer/dependency relationship** (Onboarding orchestrates the workflow, Documents stores/validates the artifacts), not a boundary violation, per the Lead Architect's G1.5 finding this authoring task was given.

## State and Lifecycle

**Current:** No state exists. No `WorkerDocument`/`Document` model, no lifecycle, no states, no transitions are implemented anywhere in the repository.

**Target lifecycle (reasoned from the confirmed capability boundary and CRR/PDD; states beyond "uploaded" and "expired" are not explicitly enumerated by either authority — labelled open, not assumed):**

- **Entry:** a `WorkerDocument` is created when a worker (or, for the contract-scan mechanism-class case, a manager) uploads a file (CRR §4 line 53, §7 line 96, §9 line 132) and it is persisted to S3 (EU) (PDD §5.2, §5.7, §8.1 line 321).
- **Expiry:** the record carries an expiry date (CRR §4 line 53: "Document upload + expiry tracking"); **the exact expiry-approach-on-crossing (warning schedule, blocking consequence, re-upload requirement) is unspecified by CRR/PDD** — contrast the fully specified contract expiry-reminder schedule (1-year/2-year, `hr/MODULE_SPEC.md` `REQ-HR-007`) which is `backend-hr`'s, not this module's (`OD-DOC-003`).
- **Categories:** CRR/PDD name only one confirmed document sub-type distinction — general document vs. work-permit document (non-EU only) (CRR §7 lines 97–98; PDD §9.3 line 389). No broader category taxonomy (e.g., ID document, proof-of-address, health document) is specified — `OD-DOC-005`.
- **Version history, permissions/access granularity, archival mechanics, and document relationships** — all four are named in this module's canonical boundary (given, not this document's to invent) but **CRR and PDD are silent on every one of them**. None is asserted as a requirement or acceptance criterion here (Constitution §6); each is recorded as an open decision/migration gap below, matching the pattern already established for other modules' silent-authority gaps (e.g., `SPEC-CRM-001` OD-CRM-01 Hotel Group data-model home, `SPEC-QUAL-001` OQ-08 tier/weighting thresholds).

**Concurrency:** not addressed anywhere in CRR/PDD for this capability — labelled unknown (`OD-DOC-011`), consistent with the same gap already recorded for `backend-hr` (`OD-HR-08`).

**Retention:** documents fall under one of CRR §25's three automatic-deletion tiers, but CRR/PDD do not explicitly state which. Reasoning (not a requirement): general uploaded onboarding documents most plausibly map to Tier 2 (5 years, "general personal/profile data," CRR §25 line 334) absent a more specific statement; work-permit documents and the contract-scan artifact could plausibly be argued Tier 3-adjacent (payroll/tax/legal-employment relevance, CRR §25 line 335) given their role in the legally mandatory employment-authorization record — **both readings are defensible from the text and neither is confirmed; this is `OD-DOC-001`, explicitly not resolved here** (mirrors `backend-hr`'s own identical unresolved tier question for the contract document itself, `OD-HR-11`).

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:** Not evaluable for current state (nothing is implemented; the one stub route unconditionally 501s). Target: DB/S3 unavailability would fail upload/retrieval operations; no degraded mode, retry policy, or partial-upload recovery behaviour is specified by CRR/PDD — labelled unknown (`OD-DOC-010`).

**Trust boundaries/authorization:** Current: the sole document-adjacent route (`backend-hr`'s stub) sits behind `authMiddleware` + `requirePermission('hr:write')` — but this gates `backend-hr`'s own boundary, not a Documents boundary, and the route never reaches functioning code. Target: CRR/PDD confirm that a worker uploads their own documents (self-service) and that a manager uploads the contract scan on the worker's behalf (mechanism-class case) — but **no document-level RBAC/permission model (who may view/edit/download a given worker's documents beyond the uploading worker and, presumably, their management chain) is specified anywhere in CRR/PDD** (`OD-DOC-007`, elevated in v0.1.1 to **blocks G2 Specification Freeze**, alongside `OD-DOC-005`, `FIND-SEC-DOC-01`). In the interim, every worker-facing `worker_id` parameter across `IF-DOC-*` interfaces MUST be self-scoped to the authenticated caller's own identity for Worker-role callers, never client-supplied (mirrors `hr/MODULE_SPEC.md` `OD-HR-10`/`FIND-SEC-HR-03`), and `IF-DOC-GetDocument`'s bare `document id` MUST be bound to an ownership/management-chain authorization check before returning a result (`FIND-SEC-DOC-01`) — see Interfaces and Contracts. Non-self uploads MUST additionally derive the acting actor's identity exclusively from the authenticated session (`RULE-DOC-08`, `FIND-SEC-DOC-02`). Special-category document applicability (if any) would require the restricted-visibility + per-view/edit-audit-log mechanism CRR §27 already mandates for special-category *fields* (lines 349–352) — unconfirmed for document *types* (`OD-DOC-002`).

**Data classification/retention:** Documents are personal data at minimum (identity/residence documents), potentially special-category depending on unresolved document-type applicability (`OD-DOC-002`). Retention-tier assignment is unresolved (`OD-DOC-001`; §25). Germany/EU-only storage is confirmed without exception (PDD §5.7 line 195, §14 line 489) — this is the one Documents-specific privacy constraint stated with certainty in the authorities. TLS-in-transit applies to Documents' own read/write operations against S3 and its own API surface — restating, not newly deriving, the same in-transit expectation Onboarding's specification states for its transmission leg ("Document uploads: transmitted over TLS (HTTPS) in transit, terminated at the platform edge," `onboarding/MODULE_SPEC.md:324`, PDD §5.2). **New in v0.1.1 (`FIND-SEC-DOC-04`):** S3 server-side encryption at rest for the identity/residence documents this module owns has no CRR/PDD statement and, unlike retention (`OD-DOC-001`), special-category applicability (`OD-DOC-002`), and S3 failure/retry (`OD-DOC-010`), previously had no open decision tracking it at all — now tracked as `OD-DOC-017`.

**Performance budgets/workload:** No explicit SLO is defined in CRR/PDD for document upload/retrieval latency or storage volume. Design intent: document volume scales with employee headcount and required-document count per worker (bounded, not request-rate-driven), similar in shape to `backend-hr`'s low-frequency, per-employee-per-year contract/payslip volume (`hr/MODULE_SPEC.md`'s own performance note). Concrete budgets are deferred to implementation and not asserted here (Constitution §6).

**Observability/audit:** No audit behaviour is implemented (nothing exists). Target: consistent with every other module's shared `AuditLog` pattern (`base-service.ts`) and with CRR §27's mandated per-view/edit audit-log entries for any special-category-classified field/document, though the latter's applicability to document types remains open (`OD-DOC-002`). *(Bullet order corrected `FIND-DOCVAL-001`, v0.1.2, to match `MODULE_SPEC_TEMPLATE.md`'s Performance-before-Observability order.)*

**Indexing capacity note (new in v0.1.1, `FIND-PERF-001`):** `IF-DOC-ListWorkerDocuments` and `IF-DOC-GetDocumentCompleteness` both filter/compute by `worker_id` plus category/status — the same missing-compound-index anti-pattern class already recorded platform-wide as `SPEC-QUAL-001` `FIND-PERF-003`. Tracked as `OD-DOC-019`: whoever authors the `WorkerDocument` Prisma model/migration MUST include a compound index on `worker_id` (+ category/status) at schema-creation time, not as a follow-on migration.

**Retrieval-mechanism note (new in v0.1.1, `FIND-PERF-002`):** `OD-DOC-010` covers only S3 failure/retry/backoff; it does not address the separate retrieval-mechanism question — presigned URL vs. app-proxied byte stream — which materially changes latency/memory/concurrency profile on every document view. Tracked as new `OD-DOC-018`.

**Retention-sweep query cost (new in v0.1.1, `FIND-PERF-004`):** `backend-retention`'s retention-sweep's (`SPEC-RETENTION-001`) query/scan cost against `WorkerDocument` rows is unaddressed here, mirroring `SPEC-QUAL-001` `FIND-PERF-002`'s O(n) rescan finding. Folded into `OD-DOC-019`: whichever field Documents writes to support tier classification (`RULE-DOC-06`) should be indexed once both the tier field is finalized (`OD-DOC-001`) and `SPEC-RETENTION-001` defines its sweep query shape — a joint forward-looking item, not fully resolvable by Documents alone (consistent with `OD-DOC-012`'s existing one-sided-boundary framing).

**Export-path scope (new in v0.1.1, `FIND-PERF-003`):** `IF-DOC-ExportWorkerDocuments`'s input is bounded per-worker by construction (a single worker id) and by GDPR Art. 15's inherently per-data-subject scope — no unbounded or multi-worker export path exists or is proposed.
