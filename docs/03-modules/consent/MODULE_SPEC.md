## Purpose and Scope

**Outcome:** Establish Consent as the single, standalone bounded context owning the full consent lifecycle — consent records, versions, granting, withdrawal, renewal, and audit history — and expose consent-state validation (e.g., "has this worker accepted today's consent notice") to every consuming module through `IF-CONSENT-*` interfaces, so that no other module builds a competing consent gate, consent-state model, or consent-adjacent persistence of its own (`ADR-015`, Decision items 1 and 6).

**In scope:**

- **The recurring/daily GDPR access-gate consent** (CRR §24; PDD §7.6, §9.3): every time a worker logs in or starts work, they must agree to the German data-protection notice (Datenschutzinformation nach Art. 13 DSGVO) to proceed; acceptance is required **once per calendar day**, not per login; declining **blocks access** and **notifies the manager**; the notice must be available in **all** languages the system supports (CRR §32 — 12 supported languages, RTL for Arabic/Urdu).
- **Consent records and their versions:** persisting which notice version a worker accepted, when, and whether by grant, withdrawal, or renewal — the `ConsentLog` entity PDD §9.3 names as "Daily consent acceptance (per day, per notice version)" is the confirmed target-state shape for at least the daily gate instance; this module owns the general consent-record/version model, of which the daily gate is one instance (`ADR-015` Decision item 1).
- **Consent lifecycle actions:** granting, withdrawal, renewal — as general lifecycle verbs this module owns for any consent instance, not solely the daily gate (`ADR-015` Decision item 1). CRR/PDD confirm the daily gate's grant/decline mechanics explicitly; withdrawal and renewal as general capabilities are named by `ADR-015`'s ownership grant but have no CRR/PDD-confirmed instance of their own beyond the daily gate's inherent per-day renewal — see `OD-CONSENT-001`.
- **Audit history:** an immutable record of every consent decision (grant, decline, withdrawal), consistent with the platform-wide "every important action is logged" mandate (CRR §30).
- **Validation:** answering "has this worker accepted today's consent notice" (and, generally, "is this worker's consent for instance X currently valid") for any consuming module or gate that needs to check consent state before proceeding (CRR §24; `ADR-015`).
- **The one-time chatbot data-processing consent question** (Onboarding `OPQ-3`, resolved by `ADR-015` to be a Consent-module product/design decision): whether engaging the chatbot requires explicit data-processing consent, and whether a decline blocks onboarding, are recorded here as an **open design decision this module must resolve** (`OD-CONSENT-002`), not answered by CRR/PDD directly and not adjudicated by Onboarding or Chatbot.
- **`IF-CONSENT-*` interfaces** consumed by Onboarding (`OPQ-3`, resolved), Chatbot (`SIR-CHAT-008`), and every module that references the daily access gate as an externally-owned precondition (Employee Management, Calendar, Notifications, Job Dispatch, Documents) — see Interfaces and Contracts.
- **Compliance's read-only governance/audit consumption** of consent state and audit history for policy governance and regulatory reporting (`ADR-015` Decision item 4) — this module exposes that read surface; Compliance does not write to it.

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6; `ADR-015`)

- **Enforcement of the access-gate consequence itself** (i.e., the actual blocking of a login/work-start action, and the UI that presents the notice) — this module owns and exposes the gating *fact* (has the worker accepted today's notice) and the withdrawal/decline *event*, but the consuming module's own authentication/session/work-start flow is what acts on that fact to block access. Compare `RULE-HR-04`'s identical pattern (HR supplies the contract-signed gating fact; Onboarding/employee-management enforce it).
- **Manager-notification delivery mechanics** — this module emits the "consent declined" fact/event; delivery of the notification to the responsible manager is Notifications' owned capability (`docs/03-modules/notifications/MODULE_SPEC.md` `TREQ-005`, `TRULE-004`; CRR §18, §24).
- **Onboarding orchestration** — the Personalfragebogen self-service form, document-collection chatbot conversation flow, application→familiarization sequencing, and the pool/claim hire-approval mechanism remain owned by Onboarding (`docs/03-modules/onboarding/MODULE_SPEC.md`); Onboarding owns no consent gate, logic, or state of its own and requests consent only through `IF-CONSENT-*` (`ADR-015` Decision item 2).
- **Chatbot conversation logic and tool execution** — Chatbot only initiates the consent flow through this module's published interfaces; it never owns consent logic or state (`ADR-015` Decision item 3; mirrors the consumption pattern `ADR-013` established for Chatbot's relationship to Onboarding).
- **Consent *governance*, policy authorship, and regulatory reporting logic** — Compliance's role, clarified (not retracted) by `ADR-015` Decision item 4: Compliance reads consent state/audit history for governance and reporting; it does not author or store consent records, versions, withdrawal, or renewal logic. `docs/03-modules/compliance/` holds only `.gitkeep`; no `MODULE_SPEC.md` exists there to correct.
- **Retention-tier deletion execution** — this module classifies consent-record retention where determinable (see `OD-CONSENT-003`) but does not execute automatic deletion; that is the Retention capability's owned mechanism (CRR §25), which itself has no registered module id or frozen specification today.
- **Employee identity, core employment fields, lifecycle status, RBAC/scope framework itself, and platform authentication** — owned by Employee Management and Authentication/User Management respectively; this module consumes, never redefines, the authenticated worker/session identity and role/scope model.
- **Every other consuming module's own domain state** — Employee Management, Calendar, Notifications, Job Dispatch, and Documents each continue to treat the daily access gate as an externally-owned precondition exactly as already written in their own specifications (e.g., `employee-management/MODULE_SPEC.md:205`, `calendar/MODULE_SPEC.md:227`); none may own consent lifecycle, records, versions, withdrawal, renewal, audit history, or validation (`ADR-015` Decision item 5).

**Non-goals:** (confirmed out of scope entirely, or explicitly excluded by CRR/PDD/ADR-015)

- Data minimization/pruning of collected fields — CRR §26 confirms "we don't need minimization," though each field must remain tied to a stated legal basis (a Compliance-governed concern, not this module's).
- Any second, competing consent gate or consent-state model inside Onboarding, Chatbot, or any other module (`ADR-015` Decision item 1 — explicitly and permanently excluded by the ratified boundary).
- Legal/DPO re-litigation of whether the daily gate's legal basis is properly "consent" versus "informational" — CRR §24 explicitly flags this as a Zirove-raised legal-mismatch concern, with the client instructing the gate be kept as specified regardless; this module implements the confirmed behaviour and does not adjudicate the underlying legal-basis question.

## Ownership and Boundaries

**Module owner:** `unassigned` — accountable owner assignment is reserved human authority (`SYNC-001`; no `CODEOWNERS`, empty `backend/package.json` author, consistent with every other module in this repository). Code-level home is the target `backend-consent` module (`backend/src/modules/consent`), which does not exist today in any form — not a stub, not a `.placeholder` file. This specification is the proposed docs↔code mapping for `backend-consent`; it is not asserted as final until G2 freeze.

**Owned state:**

- Consent records: worker id, consent purpose/instance (e.g., "daily access gate," "chatbot data-processing consent"), notice version, decision (grant/decline/withdraw), and timestamp.
- Consent-record versions: the mapping of notice text/version to the specific consent instances accepted or declined against it.
- Audit history: the immutable, chronological log of every consent decision, per worker and per consent instance.
- Consent-validation state derivable from the above (e.g., "is today's daily-gate consent currently granted for worker X").
- The notice content/version catalog itself, in all 12 supported languages (content and versioning; not client-side rendering).

**Consumed state (owned elsewhere, referenced, never redefined):** the authenticated worker/session identity that every consent record is keyed to (Authentication/User Management); the notice text's underlying legal/DPO-approved copy, which this module stores and versions but does not author as legal content (client/business-owned, per CRR §24's Zirove flag); role/scope for any future `consent:*`-style permission (Authentication/Authorization); the responsible-manager identity a decline notification targets (Employee Management's hotel/manager association).

**Permitted writes:** only to this module's owned state above, and only through its own interfaces. This module never writes the employee/employment record, the authenticated session itself, the notification-delivery mechanism, or any other module's domain state.

**Boundary/non-responsibilities:** this module does not perform authentication, session management, RBAC/scope enforcement itself, notification delivery, retention-deletion execution, onboarding orchestration, chatbot conversation logic, or consent-policy authorship/regulatory-reporting logic (that is Compliance's governance role, read-only against this module). It holds only the consent-lifecycle, consent-record, version, and audit-history state described above, and the read/validation surface every consuming module uses. Per `ADR-015` Decision item 6, no module other than `backend-consent` may own consent lifecycle, records, versions, withdrawal, renewal, audit history, or validation — this is a settled, non-competing boundary, not one this specification itself adjudicates or re-opens.

## State and Lifecycle

**States (consent-record-level, owned here):**

- **(none) → Requested** — a consuming module invokes `IF-CONSENT-RequestConsent`; no decision has yet been made (target-state; no CRR/PDD-confirmed intermediate persistence step is named beyond presenting the notice — `[OPEN]`, `OD-CONSENT-007`, whether a "requested-but-undecided" state is itself persisted or purely transient).
- **Granted** — worker has accepted the presented notice/version for the given consent instance and calendar date (or, for a one-time instance, permanently until withdrawn).
- **Declined** — worker has declined; access is blocked for that calendar day (daily gate) and a manager-notification fact is emitted.
- **Withdrawn** — a previously granted consent has been revoked by the worker (general lifecycle capability; concrete trigger scenario beyond the daily gate's inherent lapse is `[OPEN]`, `OD-CONSENT-001`).
- **Lapsed/Renewed** — for the daily gate specifically, a prior day's `Granted` state does not carry forward; a fresh `Granted`/`Declined` decision is required each calendar day (CRR §24, line 326); this is the daily gate's built-in renewal cycle, not necessarily a separate persisted "Lapsed" state — `[OPEN]`, `OD-CONSENT-007`.

**Transitions:**

- `(none) → Requested` — a consuming module needs a consent decision and calls `IF-CONSENT-RequestConsent`.
- `Requested → Granted` — worker accepts the presented notice/version.
- `Requested → Declined` — worker declines; access-block fact and manager-notification fact/event are produced (`RULE-CONSENT-03`).
- `Granted → Withdrawn` — worker later revokes a standing consent (general capability; concrete trigger `[OPEN]`, `OD-CONSENT-001`).
- `Granted (day N) → Requested (day N+1)` — the daily gate's calendar-day renewal cycle; no explicit "Lapsed" transition is confirmed as a distinct persisted state versus simply requiring a new record each day (`OD-CONSENT-007`).

**Invariants:** no worker may be granted daily-gate access on a calendar day without a `Granted` consent record dated that same calendar day and matching the current notice version (CRR §24); a `Declined` decision on the daily gate always produces both an access-block fact and a manager-notification fact — neither may fire without the other (`RULE-CONSENT-03`); no consent record, once written, is ever edited or deleted (`RULE-CONSENT-05`).

**Concurrency:** not addressed in the authoritative documents for this module specifically; labelled unknown (Constitution §6, `OD-CONSENT-008`) — e.g., simultaneous grant/decline submissions for the same worker/day are not specified.

**Retention/migration:** no CRR/PDD-confirmed retention tier is explicitly assigned to consent records specifically (CRR §25 names only Tier 1/2/3 for shift coordinates, general personal/profile data, and payroll/tax-adjacent fields respectively — consent records fit none of these named categories cleanly) — see `OD-CONSENT-003`. No prior `ConsentLog` data exists in the current schema to migrate; this is entirely net-new capability, built pre-launch with no production data (CRR §34 pattern, mirrored from every other net-new module in this repository; PDD §10).

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:**

- Worker declines the daily gate → access blocked for that calendar day; manager notified (fact/event emitted by this module; delivery owned by Notifications) (CRR §24; `RULE-CONSENT-03`).
- Notice content unavailable in the worker's language → no confirmed fallback behavior exists in CRR/PDD; labelled unknown — `[OPEN]`, `OD-CONSENT-009`.
- A consuming module (Onboarding/Chatbot) calls `IF-CONSENT-RequestConsent`/`IF-CONSENT-CheckStatus` and this module is unavailable → no confirmed fallback/degraded-mode behavior exists; `[OPEN]`, `OD-CONSENT-006`.
- Current-state: this module does not exist in code; every interface listed above is target-state only.

**Trust boundaries/authorization:** every `IF-CONSENT-*` interface's worker-id parameter MUST be derived from the calling module's own already-authenticated session/context — never accepted as an unverified client-supplied field for a different worker — mirroring the precedent set by `docs/03-modules/hr/MODULE_SPEC.md`'s `RULE-HR-14`/`FIND-SEC-HR-02` and the IDOR-scoping guidance in its `OD-HR-10`/`FIND-SEC-HR-03`. This module's `IF-CONSENT-RecordDecision` and `IF-CONSENT-WithdrawConsent` are self-scoped-only (a worker records or withdraws only their own consent); `IF-CONSENT-CheckStatus`/`IF-CONSENT-RequestConsent` are invoked by a consuming module's own trusted backend logic (in-process or worker-facing per that module's own trust boundary), not by an arbitrary caller supplying an unrelated worker id. `IF-CONSENT-GetAuditHistory` is exposed to Compliance/Admin as a read-only surface only (`RULE-CONSENT-08`) — no write path exists for that consumer role, by design. **G4 Security Review finding:** the "Admin" caller class named in the interface table has no defined RBAC scope, role model, or per-worker authorization boundary anywhere in this specification or in `OD-CONSENT-011`'s current framing — this is a real specification gap, not a disclosed-and-accepted unknown. Until `OD-CONSENT-011` is resolved with an explicit `consent:*`-style permission and scope definition, **no implementation may grant "Admin" read access to `IF-CONSENT-GetAuditHistory`**; Compliance's governance-scoped read path (`ADR-015` Decision item 4) remains the only authorized caller of this interface.

**Data classification/retention:** Germany-only, consistent with every other module in this platform; no data leaves the EU/EEA. Consent records are not themselves special-category data (Konfession, disability, health data per CRR §27) — they record only notice-acceptance metadata (worker id, instance, version, decision, timestamp). Retention tier for consent records specifically is unresolved against CRR §25's three named tiers — see `OD-CONSENT-003`.

**Performance budgets/workload:** no explicit SLO is defined in the authoritative documents. Design intent: the daily gate's `IF-CONSENT-CheckStatus` query is invoked at every login/work-start, so it is a high-frequency, low-latency read relative to most other modules' request volumes — this is a design-intent inference from the gate's "every login/work-start" trigger (CRR §24), not a CRR/PDD-confirmed budget; concrete budgets are deferred to implementation and not asserted here (labelled unknown, Constitution §6).

**Observability/audit:** every consent decision (grant, decline, withdrawal, renewal) should be logged immutably via the existing audit framework, consistent with the platform-wide "every important action is logged" rule (CRR §30). No admin-facing log-viewer screen exists platform-wide (CRR §30) — this module does not introduce one. Given this module's role as the sole compensating record for the access-gate's legal-basis question (CRR §24's Zirove-flagged legal-mismatch concern), its audit-history completeness is a first-order design concern, not an afterthought — mirroring `docs/03-modules/hr/MODULE_SPEC.md`'s `RULE-HR-15` treatment of its own trust-boundary-critical audit requirement.
