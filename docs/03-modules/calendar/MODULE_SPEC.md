## Purpose and Scope

**Outcome:** The authoritative scheduling surface of the Workforce Operations Platform — the per-worker, per-day **calendar** that managers use to place workers directly (the primary assignment path), that workers use to view their own days and to self-mark **sick** or **vacation**, and the derived **today-only red/green availability** signal other modules read. Today this behaviour is **entirely unbuilt**: the `calendar` code module is a route-registered stub whose only shape models manager-entered reception data, not scheduling (CRR §13, §20, §22; PDD §4.5, §7.2, §9.3).

**In scope:**

- **Current:** A route-registered `calendar` module mounted at `/api/v1/calendar` exposing two authenticated, hotel-scoped endpoints (`GET`/`POST /hotels/:hotel_id/operations`); both delegate to `CalendarService` methods that throw `NotImplementedError` (HTTP 501) (`backend/src/modules/calendar/{routes,controller,service}.ts`; `backend/src/routes/v1/index.ts:36`).
- **Current:** A single type, `DailyOperation { id, date, room_count, checkout_count, stay_over_count, notes? }` (`backend/src/modules/calendar/types.ts`), which shapes **manager-entered daily reception/operations data** (checked-out rooms, long-stay guests — CRR §19), **not** calendar scheduling entries. This drift is recorded as OD-CAL-10.
- **Target:** The **weekly-plan calendar view** — the manager-facing surface for building a hotel's day-by-day plan. The **direct assignment write itself** (creating the `WorkerAssignment`/`CalendarEntry` with no worker accept step, no broadcast) is a **Job Dispatch capability** invoked from this surface, not a Calendar-owned write (`ADR-021`; CRR §13 §192–§198; PDD §4.4, §7.2). Calendar reads assignment facts to render the plan.
- **Target:** A worker's **own-calendar view** (CRR §13 §197; PDD §4.5), composing this module's absence entries with assignment facts read from Job Dispatch/assignments.
- **Target:** **Sick/vacation self-marking (Calendar-owned)** — a worker marks a **current or future** day as `sick` or `vacation` (type mandatory) in this module's own `state-calendar-absence`; the manager is notified; no cap, no advance notice, no approval; vacation is a label only with **no balance tracking** (CRR §22; PDD §4.5). Any existing same-day assignment is auto-cancelled **by emitting `EVT-CAL-SickVacationMarked`**, which the assignment owner (Job Dispatch/assignments) consumes — Calendar does not write assignment state (`ADR-021`).
- **Target:** The **today-only red/green availability read-model (Calendar-owned)** — Red = not available today, Green = available today; **derived** by this module from same-day assignment facts (read from Job Dispatch/assignments) and its own sick/vacation state, and **not** re-computed for the calendar date being viewed (CRR §20; PDD §4.10). Ownership of this read-model is settled to Calendar by **`ADR-021`**, resolving `SPEC-EMP-001` `OD-EMP-07`.
- **Out of scope (owned by Job Dispatch, per `ADR-021`):** the `CalendarEntry` persistence model, `WorkerAssignment` creation, and the partial unique index enforcing one active assignment per worker per day (PDD §9.3, §9.4). Calendar references but does not own or write these.

**Out of scope:** (owned elsewhere and referenced, never redefined — Constitution §6)

- **Broadcast job requests** (gap-fill dispatch), the skill × headcount request, eligible-worker computation, first-accept slot locking, the 6-hour auto-close, and "requirement fulfilled" messaging. Owned by the **Job Dispatch / work-requests** module (CRR §13 Fallback; PDD §4.4, §7.3). Calendar only supplies/reads the same-day-assignment fact that gates exclusivity.
- **The assignment record itself** (`WorkerAssignment`), the **`CalendarEntry` model**, assignment creation, and **daily-exclusivity enforcement**. Owned by the **assignments** module / the FROZEN Job Dispatch spec (`state-worker-assignment`, `DEPENDENCY_GRAPH.yaml`; `SPEC-JOB-DISPATCH-001@0.3.1`). Settled by `ADR-021`: a direct calendar-surface placement is effected through Job Dispatch's assignment-creation path; Calendar neither creates nor writes these (was `OD-CAL-03`, RESOLVED).
- **Skill-based eligibility** for broadcasts (matching skill ∧ free that day). Owned by Job Dispatch, reading skills from Employee Management (CRR §13; SPEC-EMP-001 `IF-EMP-GetSkills`).
- **Push-notification delivery** of the sick/vacation manager alert. Owned by the **Notifications** module (push-only; CRR §18); Calendar triggers, Notifications delivers (OD-CAL-06).
- **Authentication, JWT issuance, role/scope claims, sessions, MFA.** Owned by Authentication/User Management (`backend/src/middleware/auth.ts`; PDD §5.3).
- **The RBAC/scope framework** and the role → permission map (`backend/src/middleware/permissions.ts`; PDD §5.4). Calendar reuses `authMiddleware` and `checkHotelAccess()`.
- **The Hotel reference** and Hotel-Group scoping (owned by `crm`; SPEC-CRM-001) and the **employee/roster record** and its skills/lifecycle (owned by Employee Management; SPEC-EMP-001). Calendar references both.
- **Manager-entered reception/operations data** (checked-out rooms, long-stay guests — CRR §19; `ReceptionData` model, PDD §9.3). The current stub's `/operations` shape models this; its owning module is an Open Decision (OD-CAL-10).
- **Attendance/geofencing, quality/ratings, analytics (incl. sick/vacation counts per hotel), retention deletion, consent gating** — each its own module; each merely reads calendar/availability facts (CRR §17, §21, §25; PDD §7.4–7.6).

**Non-goals:** (confirmed out of the platform entirely — CRR §22, §13 Removed-from-jobs, Explicit Non-Goals)

- **Leave-balance tracking** and any remaining-leave-days accounting (CRR §22 §306; Explicit Non-Goals). Vacation is a label only.
- **Leave-approval workflow** — no approval step; the manager is only notified after the fact (CRR §22 §305, §307).
- **Shift swaps** and **coverage planning** (CRR §22 §308–§309; Explicit Non-Goals).
- **Recurring / repeating schedule patterns** — manual day-by-day entry only (CRR §13 §226, §22 §310).
- **A formal job status state machine** (Open→Assigned→In Progress→…) — the rest is handled manually (CRR §13 §225).
- **Rooms/floors/buildings/zones** scheduling (CRR §11; PDD §9.5 notes only future extensibility, out of scope now).
- **Doctor's note / sick-note health data** — sick is a plain calendar flag to avoid storing sensitive health data (CRR §22, §27 §353).

## State and Lifecycle

**Current (repository):** no domain state. The two endpoints are stubs; a call transits `authMiddleware → checkHotelAccess() → CalendarService.*` and terminates in `NotImplementedError` (HTTP 501). No `CalendarEntry` table, no availability derivation, no scheduled job.

**Target — Calendar-owned `state-calendar-absence` states (per worker, per day):**

- **sick** — worker-marked day; stores no health data; emits `EVT-CAL-SickVacationMarked`.
- **vacation** — worker-marked day; label only; no balance tracking; emits `EVT-CAL-SickVacationMarked`.

The **assignment** state (and its states/exclusivity) lives in the Job-Dispatch-owned `CalendarEntry`/`WorkerAssignment`, not in this module (`ADR-021`).

**Target — transitions (each audit-logged; each from a confirmed action):**

- `(none) → sick | vacation` — worker self-mark on a current/future day (`RULE-CAL-03`); emits `EVT-CAL-SickVacationMarked`.
- A **past** day cannot receive a new sick/vacation mark (`RULE-CAL-03`).
- `assignment → cancelled` is a **Job-Dispatch/assignments transition**, triggered by that owner consuming `EVT-CAL-SickVacationMarked` (`RULE-CAL-04`) — recorded here only as a downstream effect, not a Calendar write.

**Invariants:** at most one active `assignment`-kind entry per (worker, day) is enforced by Job Dispatch's partial unique index (PDD §9.4) — not by this module; a worker ends up not simultaneously assigned and on-leave for a day once the assignment owner has consumed the mark event (converged at the assignment locus, `ADR-021`); the availability read-model is **today-only** and independent of the viewed date (`RULE-CAL-08`); no leave balance is tracked; no recurring entries are generated.

**Concurrency:** Calendar writes the absence entry and emits `EVT-CAL-SickVacationMarked` atomically within its own boundary; the same-day assignment cancel is performed by the assignment owner on consuming the event (eventually consistent at the assignment locus), replacing v0.1.0's cross-module single transaction (`ADR-021`). The broadcast last-slot race and daily-exclusivity write path are resolved in Job Dispatch (Redis slot lock, `SELECT … FOR UPDATE` fallback; partial unique index; PDD §7.3, §9.4) — **not** here.

**Retention/migration:** pre-launch, no production calendar data (PDD §10); introducing `CalendarEntry` is additive. Sick flags store no sick-note/health data by design (CRR §27 §353). Sick/vacation counts feed analytics but are not separately retained by this module.

## Failure, Security, Privacy, and Performance

**Failure modes/recovery:**

- **Current:** every functional call returns 501; there is no data path to fail. (This is itself the top migration risk: the module is named/registered but does nothing.)
- **Target:** past-day sick/vacation mark → rejected; second same-day assignment → rejected (exclusivity, enforced by Job Dispatch); Calendar's own absence-write + event-emit is atomic within its own boundary only — it performs no cross-module transaction, and never rolls back on the consumer's account (`ADR-021`); if the assignment owner fails to cancel on consuming `EVT-CAL-SickVacationMarked`, that is reconciled at the assignment locus, not by Calendar; manager notification undelivered → calendar state stands, alert retried by Notifications; unknown hotel/worker → placement rejected (raised by Job Dispatch).

**Trust boundaries/authorization:** reuse existing authentication (`authMiddleware`) and hotel-scope authorization (`checkHotelAccess()` — admin/manager/checker bypass the membership check, `permissions.ts:103-108`). Deny-by-default on role × hotel/group scope. A worker may read/write only their **own** calendar (self sick/vacation); managers place workers within their hotel scope. The Regional-Manager scheduling scope across a Hotel Group is unmodeled (no enum token — SPEC-CRM-001 role gap; OD-CAL-07).
