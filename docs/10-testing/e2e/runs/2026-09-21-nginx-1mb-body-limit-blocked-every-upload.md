# E2E Run — 2026-09-21 — every upload through the API was blocked by nginx

- **Reported as:** "in the checker app when I'm trying to check a room and submit it, it says
  request failed".
- **Environment:** production, `api.deepcleaninghub.de`. Diagnosed and fixed on the live host
  over SSM.
- **Executed by:** project owner (manual, on a real iPhone), agent (Claude Code) diagnosing.
- **Scope:** one symptom. NOT a run of the numbered scenarios.

## Result

| Scenario | Result | Notes |
|---|---|---|
| 00–20 | NOT RUN | Out of scope |
| — (ad-hoc) checker submits a room inspection with photos | **DEFECT FOUND, FIXED** | nginx 413, fixed on the host |

## The defect

`POST /api/v1/quality/inspections` returned **413 Payload Too Large**, eight times, and the
request **never reached Express** — the last one the application logged was 1 September. The
client showed its generic `errors.requestFailed` string because the response carried no
recognisable error code; it had never been generated by the app.

```
[21/Sep/2026:20:46:11] POST /api/v1/quality/inspections 413
[21/Sep/2026:20:46:18] POST /api/v1/quality/inspections 413
...  8 attempts, all 413
[21/Sep/2026:20:47:01] POST /api/v1/documents/workers/<id>/documents 413
```

**Root cause.** In the live `/etc/nginx/sites-enabled/default`, the `location /` that proxies
everything to the API on `:3001` set no `client_max_body_size`, so nginx applied its **1 MB
default**. The only occurrence of that directive anywhere on the box was
`snippets/version-control.conf` (`1024M`), which covers daiwi's `/install` and
`/version-control` locations and never applied to the API.

The application, meanwhile, accepts far more:

| Upload | App limit | nginx allowed |
|---|---|---|
| Inspection photos | 10 MB each, up to 6 (`quality/types.ts`) | 1 MB |
| Worker documents | 10 MB (`documents/upload-policy.ts`) | 1 MB |
| Profile photo, HR contract scan | 10 MB | 1 MB |

A single iPhone photo is 2–5 MB, so **this path could never have worked**. Small PDFs passed,
which is why document upload appeared to work during onboarding and failed on scans and photos.

## Why the repository could not have caught it

`nginx/hotelcrm.conf` in this repository **does** carry `client_max_body_size 100M` (line 45).
That file was written for `api.hotelcrm.app` and was never deployed; the live config is a
hand-written one for `api.deepcleaninghub.de` that never inherited the directive. This is the
same class of problem as `.env` on the host: a config bug that no PR can fix and no test can
see, because the authoritative copy is not in the repository.

## The fix

`client_max_body_size 64M` added to the API's `location /`, with the reasoning inline. 64M is
the app's own worst case (6 × 10 MB plus multipart overhead) rather than an arbitrary large
number — nginx should not accept what the application will reject.

**Verified at the edge**, not from the config file:

| Probe | Result |
|---|---|
| 3 MB → `/quality/inspections` | **401** — all 3,145,929 bytes reached Express |
| 3 MB → `/documents/workers/*/documents` | **401** — same |
| 70 MB → `/quality/inspections` | **413** — the new ceiling holds |

A 401 is the correct outcome for an unauthenticated probe: it proves nginx forwarded the whole
body instead of refusing it.

## Two notes for whoever touches nginx next

- **Never leave a backup inside `sites-enabled/` or `sites-available/`.** nginx globs those
  directories, so `default.bak.<stamp>` is parsed as a second config and fails with
  `duplicate listen options for [::]:443`. That happened during this fix; `nginx -t` caught it
  and the reload was not performed. Backups now go to `/var/backups/nginx/`. Two stale
  `.bak` files from 2026-08-30 were found in `sites-available/` and removed at the same time.
- **Always `nginx -t` before `systemctl reload`,** and restore on failure. The script used here
  did both, which is the only reason a mistake mid-change cost nothing.
