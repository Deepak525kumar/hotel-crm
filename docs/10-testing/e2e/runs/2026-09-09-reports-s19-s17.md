## Defect found and fixed: every report had a blank worker column

`GET /reports/data?dataset=assignments` returned rows whose `worker` was `null` — for every
row. Verified at the data layer rather than inferred: the database held 10 assignments in
2026-09-02..03, the endpoint returned exactly 10 for a range containing them and 0 for a
range excluding them, and all 10 carried `"worker": null`.

Cause: `AssignmentDto` exposes `worker_id` and no name, and `CalendarAbsenceDto` exposes
`worker_id`/`marked_by_id` and neither name. The reports module cannot reach into Users, so it
emitted nulls. **A manager exporting "who was absent last month" would have received a column
of blanks.**

No test could have caught this. A report of zero rows and a report with blank names are
indistinguishable to any assertion about row counts, which is exactly what the unit tests
assert.

Fixed by having each owning module expose its own data, following the `assigned_by_name`
precedent already in `AssignmentDto`:

- `assignments`: `worker_name`, resolved in the **same** `findMany` that already batch-loads
  assigner names — one union of ids, no extra round trip.
- `calendar`: `worker_name` / `marked_by_name` via two small joins on the list paths.

Re-verified live: 10/10 rows now carry the worker name.

**A rejected first attempt is worth recording.** The reports module initially resolved names
itself via `userService.listUsers({ page: 1, limit: 100 })`. That looked right and was wrong:
this platform has 610 workers, so the people in any given report are usually not on page one.
It returned nulls just as before. The lesson is that "bounded by one page" is only a bound if
the population is smaller than the page.

## A false defect I reported to myself, then disproved

The first Step 6 comparison showed the admin-created applicant with **no** target hotel or
group while the manager-created one had both — which looked like the admin path silently
dropping targets, contradicting scenario 19's already-ticked "target fields recorded".

It was my error. The API takes `hotel_id` / `hotel_group_id`; I sent
`target_hotel_id` / `target_hotel_group_id`, which do not exist. The manager path recorded
targets because it derives them from the **creating actor's own scope**, which an admin does
not have. Re-run with the documented field names, the admin path records both.

Recorded because the near-miss is the point: an unfamiliar field name and a scope-derived
default produced a difference that looked exactly like a product defect.

## 19 Step 6 — the previously unchecked box

Two applicants created through the real endpoint, identical in everything routing keys on:

```
AdminMade2 | tgt_hotel=cmtk51klg… | tgt_group=cmtk51kkj… | created_by=ADMIN
MgrMade    | tgt_hotel=cmtk51klg… | tgt_group=cmtk51kkj… | created_by=MANAGER
```

Same role, same target hotel, same target group; they differ only in `created_by`. Since
routing keys on the applicant's role and target, the resolver receives identical inputs and
must produce the same reviewer set.

**Honest limit:** this verifies the routing INPUTS are identical, not the resolver's output
side by side. Both records are `PENDING` and unsubmitted, and the review queue only lists
applicants past `submitted_for_review_at` — reaching that needs the full document lifecycle
(scenario 01). The resolver itself is covered by scenario 03. The box is now defensible but
the side-by-side queue comparison remains unrun.

is recorded here for the owner.
