# Context Management Layer (`.claude/context/`)

**Status:** Executable mechanism operationalizing [Context Artifacts](../constitution/CONTEXT_ARTIFACTS.md) (canonical policy).
**Introduced:** framework 1.5.0 (see [../VERSION.yaml](../VERSION.yaml)). Additive; extends the 1.2.0 Context Artifacts and never overrides them.
**Change class:** Non-constitutional framework addition (see [ADR-020](../../docs/14-governance/architecture-decisions/ADR-020-context-management-layer.md)).

## What this is

Before 1.5.0 the platform *defined* reusable, revision-bound Context Artifacts (Boot Context, Evidence Package, Dependency Context, Module Memory, …) in [`../constitution/CONTEXT_ARTIFACTS.md`](../constitution/CONTEXT_ARTIFACTS.md), but *which* artifacts a given workflow needs was expressed only in prose scattered across each workflow's "Context Packages" / "Inputs" sections. Every workflow re-derived its own load set.

The Context Management Layer makes that load plan **declarative, generated, and executable**. It adds no policy: it is the machine-readable projection of the constitutional artifacts plus one deterministic engine that resolves them.

```
.claude/context/
  BOOT_MANIFEST.yaml          # authored: minimum boot document set (per framework version)
  EXECUTION_MANIFEST.yaml     # authored: minimum artifact set per workflow
  ARTIFACT_DEPENDENCIES.yaml  # authored: artifact dependency + invalidation graph
  SESSION_CONTEXT.yaml        # GENERATED (git-ignored): current run's loaded working set / checkpoint
  CACHE_STATE.yaml            # GENERATED (git-ignored): computed cache validity for the current revision
.claude/tooling/
  context-loader.js           # the single deterministic engine (resolve / measure / validate / emit / prune)
  context-loader.config.json  # repository-specific paths + token-cost model
```

## Authored vs generated

| File | Kind | Authoritative for | Regenerated by |
|---|---|---|---|
| `BOOT_MANIFEST.yaml` | authored framework policy | the boot document set | — (edited by hand, `--validate` guards it) |
| `EXECUTION_MANIFEST.yaml` | authored framework policy | the per-workflow load plan | — |
| `ARTIFACT_DEPENDENCIES.yaml` | authored framework policy | artifact dependency/invalidation edges | — |
| `SESSION_CONTEXT.yaml` | **generated**, git-ignored | *nothing* — projection of [`../knowledge/SESSION_STATE.yaml`](../knowledge/SESSION_STATE.yaml) | `context-loader.js resolve --emit` |
| `CACHE_STATE.yaml` | **generated**, git-ignored | *nothing* — projection of [`../knowledge/SYNC_STATE.yaml`](../knowledge/SYNC_STATE.yaml) `cache_state` | `context-loader.js resolve --emit` |

The two generated files never hold unique authority — they are advisory, reconstructable checkpoints (CONTEXT_ARTIFACTS.md §1.5 fail-safe) and are `.gitignore`d. Deleting them changes nothing; the next `--emit` rebuilds them. The authoritative session/cache records remain [`SESSION_STATE.yaml`](../knowledge/SESSION_STATE.yaml) and [`SYNC_STATE.yaml`](../knowledge/SYNC_STATE.yaml) — no duplicate authority is created.

## How each requested behaviour is delivered

| Behaviour | Mechanism |
|---|---|
| deterministic context loading | `resolve --workflow <id>` → the exact minimum document + artifact set, content-addressed (no heuristics) |
| artifact-level dependency loading | `ARTIFACT_DEPENDENCIES.yaml` `depends_on` edges, transitively expanded by the loader |
| lazy loading | `load: lazy` documents are listed but resolved on demand, not at boot |
| reuse of already-validated context | warm/cold split from the active [Repository Session](../knowledge/SESSION_STATE.yaml); warm artifacts are never reloaded |
| delta loading | resolved set minus the prior `SESSION_CONTEXT.yaml` checkpoint |
| revision-aware loading | `baseline_revision` (from `SYNC_STATE.yaml` `cache_state`) vs. `--head`; a mismatch marks revision-scoped caches cold |
| cache invalidation | `invalidated_by` bindings, cross-checked against `SYNC_STATE.yaml` `context_invalidators` |
| session checkpointing | `--emit` writes `SESSION_CONTEXT.yaml` |
| automatic context pruning | `--prune` drops checkpoint artifacts not in the current resolved set |
| rebuild after synchronization | [repository-synchronization](../workflows/repository-synchronization.md) re-runs `resolve --emit` on rebind |
| measurable minimisation | `--measure` reports reduction vs. a naive full load |

## Commands

```sh
# Minimum load set for a workflow (deterministic loading, delta, warm reuse)
node .claude/tooling/context-loader.js resolve --workflow preflight

# Persist the checkpoint + cache-state projection, pruning stale artifacts
node .claude/tooling/context-loader.js resolve --workflow documentation --emit --prune

# Measurable reduction across every workflow
node .claude/tooling/context-loader.js --measure

# Structural validation (CI job `context-manifest`; G4 consistency sub-check)
node .claude/tooling/context-loader.js --validate
```

## Integrity

`--validate` is a deterministic, dependency-free check enforced two ways, exactly as the [repository-integrity](../tooling/repository-integrity-check.js) gate is (ADR-019 precedent): as a sub-check owned by the Consistency Reviewer at G4 (reused unchanged at G6/G9), and independently by CI on every pull request. It fails the build if any manifest references a missing file, any workflow lacks an entry, the manifest framework version drifts from `VERSION.yaml`, or an `invalidated_by` trigger is absent from the canonical `context_invalidators` list.

## Fail-safe

Absent this layer entirely (no `.claude/context/`, no loader), the platform degrades to pre-1.5.0 behaviour: read every authoritative document. The layer can only ever *reduce* what is loaded, never gate correctness — a stale or missing manifest/checkpoint forces full re-derivation, which is exactly today's behaviour (CONTEXT_ARTIFACTS.md §1.5).
